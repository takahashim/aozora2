# 設計ノート: パーサの層構造（記号解析と意味解釈の境界）

> **この文書は権威を持たない書き捨ての参考資料である。** 現状の実装を読み解くための
> 案内であり、規範ではない。実装（コードとテスト）と食い違ったらこの文書が古い。
> 更新の義務は負わない——古くなったら捨て、必要ならコードから書き直す。
> 一次資料はコーパスとソースコード（docs/architecture.md §1）。

作成 2026-07-28。青空文庫テキストを Aozora AST に変換するまでの層と、各層が
**何を根拠に**解釈を決めているか（記号の形／有限表／文字種／文字列照合）、および
参照実装の緩さをどこで再現しているかを記す。設計判断の共有が目的。

前提: 本実装は Ruby 版 `aozora2html` の**バイト一致**を目標とした移植。参照実装は形式文法を持たず、
**行指向の緩い変換器**（不正入力でも出力を出す。不均衡 div もそのまま）。したがって
「ABNF で構文を決めて外れた入力を排除する」方式は採らない。

## 全体の層

```
行テキスト
 ① tokenizer            記号の入れ子を再帰下降で認識。command 中身は不透明な文字列のまま
      Vec<Token>         Text / Ruby / PrefixedRuby / Command / Gaiji / Accent
                         （｜ の一時マーカー RubyPrefix は fold で畳まれ、外へは出ない）
 ② parse_raw_nodes      command 文字列を型付きマーカーへ解釈（行内・忠実、前方参照は未解決）
      Vec<Node>          BlockStart / BlockEnd / UnresolvedReference / Gaiji / Accent 変換 …
 ③ resolve_references   ルビ親文字の吸収・注記付き範囲・「対象」に傍点 の前方参照解決
      Vec<Node>          （末尾からの接尾辞照合・文字種規則・失敗は Note に落とす）
 ③'resolve_inline_ruby  ③で装飾タグが生まれて初めて親文字を取れるようになったルビを再解決
      Vec<Node>          （呼び出し元が③の直後に必ず呼ぶ 2 パス目）
 ④ lower_to_blocks      行をまたぐブロック構造の確定（不均衡は quirk 扱い）→ to_inlines
      Vec<Block>         （Aozora AST）
```

- ③/③' は**④の行ループの中で 1 行ごとに走る**（`lower.rs`）。図は概念的な段階を示す。
- 「**記号の形で決まる前段／文字種と照合で決まる後段**」という分離が、
  おおむね **①** と **③** として実現されている。どちらの規則も決定的。

## 各層の性質

### ① tokenizer — 記号の再帰的構造認識
- 認識する記号: `《…》`（ルビ）・`｜…《…》`（明示ルビ）・`※［…］`（外字）・`〔…〕`（アクセント）・
  `［＃…］`（コマンド）。**入れ子は再帰的に再トークナイズ**（`tokenize_children`、base offset で
  絶対 span も付与）。
- **`Command` の中身は生文字列のまま**で、意味（傍点か見出しか）は**一切解釈しない**。
- `［＃…］` の対応括弧はバランスを取って厳密にネスト。ここは決定的。
- **`｜`（明示ルビ前置）は字句走査ではマーカー `RubyPrefix` のみ**。親文字の確定は直後の
  畳み込みパス `fold_prefixed_ruby`（「`《》` から後方へ最も近い `｜`」という決定的規則）が行う。
  字句走査自体を単純に保つための 2 段構成（[spec-tokenizer.md](spec-tokenizer.md)）。
- **アクセント `〔…〕` の判定はアクセント表（`ACCENT_TABLE`）を参照する厳格な規則**。
  「中身が表の並びを含むときだけ Accent」という決定的な定義で、曖昧さは無い（後述 §）。
- **参照実装の緩さがそのまま残るのは未閉じ `〔` の行末延長のみ**（後述 §）。

### ② parse_raw_nodes — command 文字列 → 型付きマーカー（忠実・寛容）
- `command_parser` が command 文字列を解釈して `BlockStart`/`BlockEnd`/`LineJisage`/
  `UnresolvedReference` 等のマーカーにする。外字トークンは Gaiji ノード、アクセントは
  `apply_accent_to_nodes` で変換。
- **行内で完結・忠実**。前方参照は未解決のまま（`UnresolvedReference`）。未知コマンドは
  弾かず、後段で `Note` に落ちる。ここも「受理/拒否」はしない。

### ③ resolve_references — 文字種と接尾辞照合による前方参照解決
> アルゴリズムの明文化は [spec-reference-resolver.md](spec-reference-resolver.md)（互換実装用）。

- `「対象」に傍点` の対象範囲を**バッファ末尾からの接尾辞照合**で探す
  （`search_front_reference`：Text の末尾一致・分割まで許す）。
- ルビ親文字を直前本文から**文字種規則**で吸収（`extract_ruby_base`）。
- 解決できなければ `Note` に落とす（`analysis` はここで「解決失敗」を検出）。
- 記号の形ではなく**文字種と文字列照合**で対象が決まる層。規則自体は決定的で、
  解決できない入力を弾かず `Note` へ落とす点が参照実装の緩さの再現にあたる。

### ③' resolve_inline_ruby — ルビ親文字の 2 パス目
- ③の時点でルビの直前が `UnresolvedReference` だと、`last_char_type()` が `None` を返すため
  親文字の抽出は**必ず失敗する**。③で装飾タグへ解決されて初めて「タグ丸ごと 1 個が親文字」を
  適用できるので、**もう一度同じ抽出を走らせる**。
  - 例: `公事根源［＃「公事根源」は斜体］《くじこんげん》` の親文字は `<span class="shatai">…</span>`。
- 呼び出し元（`lower.rs` / `strip.rs` / `html/block_renderer.rs`）はすべて③→③'の順で呼ぶ。

### ④ lower_to_blocks — 行をまたぐ構造（quirk 許容）
- 平坦なマーカーを入れ子ブロックへ畳む。閉じ忘れ・不均衡は**弾かず** quirk として処理し、
  診断（`LowerDiagnostic`）は横に出すだけ（変換は止めない）。

## バイト一致の契約と「弾かない」原則
全層を通じて**入力を拒否しない**。参照実装が黙って出力するものは同じく出力する。これは
オラクル 17361/17453 exact の前提であり、①〜④が不正入力を弾かないのは参照実装の緩さを
再現するためである。

## 診断（変換に影響しない副線）

変換パスとは別に、`analysis` がエディタ支援向けの診断を出す。**`convert()` の出力には
一切影響しない**（オラクル不変）。現在 4 種:

| コード | 出所 | 内容 |
|---|---|---|
| `unresolved-reference` | ③ | 前方参照の対象が見つからず `Note` に落ちた |
| `unresolved-gaiji` | ② | 面区点にも U+ にも解決できない外字 |
| `unclosed-accent` | ① | 同一行で閉じない `〔…`（複数行アクセント／閉じ忘れ） |
| `unclosed-block` | ④ | EOF で閉じられなかったブロック（`LowerDiagnostic` 由来） |

「緩いまま変換しつつ、問題は診断で可視化する」のが本実装の基本姿勢。厳格化したい場合は
**変換を変えるのではなく、この診断を弾く根拠に使う**（→次節）。

## 記号解釈の厳格化 — 検討と結論（実測済み）

①の記号解釈について「決定的な規則として定義しきれるか」をオラクル実測で検討した。
**3 つとも結論が出ており、未検討の候補は無い**。
測定は `aozora-htmlcheck --oracle-dir oracle` の exact 数（ベースライン 17361/17453）。

| 対象 | 実験の内容 | exact | 差分 | 状態 |
|---|---|---|---|---|
| 明示ルビ 多重 `｜` | C: 規則を撤去（最初の `｜`→次の `《`） | 17360 | −1 | **厳格化済み**（後方規則へ書き換え） |
| アクセント 中身依存判定 | A: 表を見ず `〔…〕` を常に Accent にする | 15601 | **−1760** | **厳格化済み**（アクセント表を仕様に含める） |
| アクセント 未閉じ行末延長 | B: 均衡 `〕` を要求する | 17360 | −1 | **方針決定済み・実施保留** |

### 明示ルビ 多重 `｜` → 実施済み（撤去ではなく決定的規則への書き換え）

- 内容: `《》` の前にトップレベルの `｜` が複数あれば、最後の `｜` からを親文字にし、前の `｜` はリテラル。
- 依存: 実測 **1 ファイル**（`001094/42602`、`…今日｜民族観念［＃…］…悲憤｜慷慨《こうがい》`）。
- **実験 C（規則の撤去）は −1 なので採用しない。** 代わりに、同じ挙動を
  「`《》` から後方へ最も近い `｜`」という**決定的な後方規則**として書き直した。
  これは挙動を変えないので **byte 一致は不変（±0）** のまま、字句走査から先読みを追放できた。
- 現在の 3 挙動はいずれもこの後方規則の帰結:
  1. **多重 `｜` は最後が親文字** … ルビから遡って最も近いマーカーを採るので、余った前の `｜` は
     自動的に `Text` に戻る（→ `test_prefixed_ruby_multiple_pipes`）。
  2. **コマンド内の `｜`/`《` は区切りでない** … `［＃…］` は 1 トークンなので中の `｜` は
     そもそもマーカーにならない＝**透過が自動**（→ `test_prefixed_ruby_pipe_inside_command_not_delimiter`）。
  3. **`《` が続かなければ `｜` はリテラル** … どのルビにも畳まれないマーカーは `Text("｜")` に戻る
     （→ `test_prefixed_ruby_without_ruby`）。
- 移行日 2026-07-28。オラクル 17361 不変で確認済み。

### アクセント 中身依存判定 → アクセント表込みで厳格化（確定）

- 規則: `〔…〕` は、中身が **`ACCENT_TABLE` の並び（`e'` 等）を含むときに限り** Accent。
  含まなければ `〔` は本文（→ `test_accent_no_mark`: `〔参考〕` はリテラル／
  `test_accent`: `〔E'difice〕` は Accent）。
- 参照する表は**有限テーブル 72 件**（`ACCENT_TABLE`）。参照実装 `aozora2html` の
  `yml/accent_table.yml` からビルド時に生成しており、定義は 1 箇所に閉じている。
- この規則は**決定的・全域的**（同じ入力なら必ず同じ判定、判定不能な入力は無い）。曖昧な推測を
  含まないので、**アクセント表を仕様の一部として含めれば厳格な規則として定義できる**——
  字句仕様がキーワード表や予約語表を持つのと同じ位置づけであり、「記号の形だけで決まらない」
  ことは厳格さの欠如ではない。
- 実験 A（表を見ずに `〔…〕` を常に Accent とする）は **−1760**。青空文庫は `〔…〕` を
  アクセント以外（編集者の角括弧・原注など）でも大量に使うため、**表を外した「記号の形だけ」の
  定義は誤り**であることの裏付けになる。正しい定義には最初から表が含まれる。
- 結論: **アクセント表込みで既に厳格**。変更不要。

### アクセント 未閉じ行末延長 → 方針決定済み・実施保留

- 内容: 対応する `〕` が無くてもトップレベルなら行末までを Accent（入れ子ではリテラル）。
  （→ `test_unclosed_accent_top_level`）
- 依存: 実測 **1 ファイル**（`000272/4363`）。参照実装は複数行 `〔…改行…〕` の 1 行目だけを
  アクセント化し、次行の `〕` はリテラルにする。
- 実験 B（均衡 `〕` を要求）は −1 で、**厳格化のコストは極小**。
- **現状**: aozora2html 互換を優先して**許容したまま**、診断 `unclosed-accent`（Warning）で
  **可視化のみ**行う（変換は緩いまま＝byte 一致維持）。
- **将来**: 複数行アクセントを禁止する方針。厳格モードは「必要になった時点で実装」（YAGNI）とし、
  実装時はこの診断の検出をそのまま弾く根拠に使う。

### 単体テストとの関係

- 決定的規則の番人: `test_accent_no_mark`（アクセント表による判定）／
  `test_prefixed_ruby_multiple_pipes` ほか `｜` 系（後方規則）。いずれも変更対象ではない。
- 唯一まだ動きうるのは `test_unclosed_accent_top_level`（未閉じ `〔` の行末延長）。
- 単体テストは局所的な番人にすぎず、**真の影響はオラクル差分**（`000272/4363` 等の実ファイル）で測る。

### まとめ

- 括弧のネスト・`｜` の後方規則は、**記号の形だけ**で決まる厳格な規則。
- アクセント判定は、**有限のアクセント表を仕様に含める**ことで厳格な規則として定義済み。
- 参照実装の緩さがそのまま残っているのは**未閉じ `〔` の行末延長のみ**。コスト −1 で
  厳格化可能で、方針決定済み・実施保留。
