## 目的と非目的

### 目的

- 互換挙動を、巨大な行ループの分岐順ではなく、**明示された制約**として記述する。
- ブロックの対応・暗黙閉じ・行結合・改行を一つの解決結果 `LowerPlan` に集める。
- Aozora AST の構築を `LowerPlan` からの純粋な写像にする。バックエンドは引き続き
  状態を持たない木歩きだけを行う。
- 各決定に根拠（どのマーカー・どの規則）を残せる形にし、診断やデバッグ時の説明を
  可能にする。

### 非目的

- ソース上の位置順を意味論から取り除くこと。開始・終端・行マージの互換挙動は、
  位置順を意味として使う。
- 汎用 SAT/SMT ソルバやバックトラックを導入すること。規則は決定的であり、線形時間の
  専用解決器で十分である。
- 現行の quirk を正規化すること。未対応の終端を捨てる、EOF で閉じる、ぶら下げの
  開始行を次行へ結合する、といった挙動は参照実装の側の挙動なので、現行再現でも
  参照互換でも制約として残す（プロファイルの区別は「互換性の不変条件」）。

したがって「順序に依存しない」とは、ソース順を無視する意味ではない。**制御フローの
偶然の順序ではなく、位置順を含む宣言済みの関係だけで結果が決まる**ことを指す。

## 全体像

```text
RawDoc
  │  行ごとの③ resolve_references → ③' resolve_inline_ruby
  ▼
MarkerFacts       位置付きの候補・マーカー・内容断片（役割の割り当て済み）
  ▼
LowerConstraints  役割、優先度、対応、包含、暗黙閉じ、行結合、改行の規則
  ▼  solve
LowerPlan          ブロック森、対応、断片、CloseKind、Break、診断
  ▼  materialize
Aozora AST
```

`solve` は実装上スタックやワークリストを使ってよい。ただしそれらは制約を効率よく
解くための内部表現であり、仕様そのものではない。仕様は `MarkerFacts` と
`LowerConstraints` として完結する。

## 用語と基本データ

### Position

すべての事実は `Position` を持つ。

```rust
struct Position {
    line: usize,       // RawDoc の本文行番号
    node: usize,       // 解決後ノード列での順序
    offset: Span,      // 同一ノード内を区別する必要がある場合の原文 span
}
```

`Position` は辞書順の全順序を持つ。この順序は入力の事実であって、解決器の実装順序では
ない。以下の「前」「後」「最も内側」はすべて `Position` と区間の関係で定義する。

### MarkerFact

`MarkerFacts` は、解決済みの各行から得る不変の事実の列である。

```rust
enum MarkerRole {
    BlockStart { kind: BlockKind, form: OpenForm },
    BlockEnd { written_kind: BlockType, explicit: bool },
    InlineRangeStart { kind: BlockType },
    InlineRangeEnd { kind: BlockType },
    LineWrap { kind: BlockKind },
    HardBreak,
    Content,
}

struct MarkerFact {
    id: FactId,
    pos: Position,
    role: MarkerRole,
    source_span: Span,
}
```

ここで `BlockEnd.written_kind` は記法に書かれた種類を保存する。一方、複数行ブロックの
終端が実際に閉じる相手は後述の制約で決めるため、両者が異なりうる。

**`role` は位置だけでは決まらない。** 同じマーカーでも、同じ行に何があるかで役割が変わる
（例: 複数行ブロックの開始は、同じ行に終端があれば開かない）。この割り当て規則が
互換性の中心なので、制約 1 として独立に定義する。

### CommandCandidate

同じコマンド文字列が複数の記法語を含むとき、②は最初に一致した `if` で決める代わりに
候補を全て列挙してよい。

```rust
struct CommandCandidate {
    result: CommandResult,
    precedence: u16,
    evidence: CandidateEvidence,
}
```

制約は「候補をちょうど一つ選ぶ」「より高い `precedence` の適格候補があれば、低い候補は
選ばない」である。現在の `parse_command` の分岐順はこの優先度表の初期値になる。従って
順序は消えないが、文法のデータとして可視化され、実装の `if` の並びから独立する。

**適格の定義**は記法語の一致ではなく、**その分岐の切り出しまで成功すること**である。現行の
振り分けは「一致したら確定」ではなく「内側の切り出しが失敗したら次の分岐へ落ちる」形で、
画像（`fig…png` を含むがファイル名や寸法の形が違う）と前方参照（対象は取れたが指定部が
どの記法にも当たらない）が該当する。記法語の一致だけを適格とすると、これらが後続の分岐へ
落ちずに注記化の経路が変わる。

`ここから…` のように**注記を返す分岐は「選択済み」であって不適格ではない**。
`［＃ここから割り注］` は注記になるのが正しく、後続の分岐へ落としてはいけない
（[spec-commands.md](spec-commands.md) の分岐 6）。

## 制約

解決器は下記の制約をすべて満たす唯一の `LowerPlan` を作る。入力が参照実装で停止する
領域でも、現行 Lowerer と同じ全域的なフォールバックを適用する。

### 1. 役割の割り当て

各マーカーの `MarkerRole` は、**その行のマーカー全体**から決める。行ごとに、次の規則を
上から順に試し、最初に当たったものがその行の役割の組を決める。この優先順は
`CommandCandidate` の優先度表と同じく宣言済みのデータであり、制御フローの偶然ではない。

種類による前提（行の形に関わらず成り立つ）:

- `ここから…` 形の開始（`is_block`）だけが複数行ブロックの開始になれる。行内形
  （`［＃中見出し］` など）は `InlineRangeStart` にしかならない。
- **割り注の開閉は常にインラインマーカー**である。ブロックの開始にも終端にもならない
  （参照 `apply_warichu` は開いているブロックに触れない。実測）。
- 複数行ブロックへ写せない種類（`block_kind_of` が `None`。縦中横、割書、装飾、
  注記付き範囲）は、**行途中では**終端として数えない。
- 行途中の地付き（`is_block` でない `Chitsuki`）は開始として数えない。行末で閉じるので、
  同じ行の `［＃ここで地付き終わり］` は前の行から続く地付きを閉じる（実測）。

行の形による割り当て（優先順）:

1. **ぶら下げ開始行**: 行に終端マーカーが一つも無く、`is_block` のぶら下げ開始がある。
   その行の他の内容は結合断片になる（制約 6）。位置は問わない。
2. **単独の開始**: 行が `is_block` の開始 1 個だけからなる。`BlockStart`。
3. **単独の終端**: 行が終端 1 個だけからなる（割り注を除く）。`BlockEnd`。
   ここでは `block_kind_of` で写せない種類も終端として扱う。行途中の規則との非対称だが、
   そうした入力は参照実装が停止するため正解が無く、現行の緩い回復を保つ（実測）。
   最終形は下記「既知の非互換と将来の統一」を見よ。
4. **未対応の終端を含む行**: 同じ行に対応する開始が無い終端が一つ以上ある。それらが
   `BlockEnd`、他は内容になる。**この行の開始は開かない**（`BlockStart` にならず、
   同一行対応も付かなければ捨てられる。実測）。
5. **行途中の開始**: `is_block` の開始があり、後ろに要素が続き、同じ行に終端マーカーが
   一つも無い（種類は問わない）。`BlockStart`。**開始マーカーの前に何があるかは問わない**
   （参照と同じ。下記「既知の非互換と将来の統一」）。
6. **行スコープ包み**: `LineJisage` があるか、行頭が行スコープ地付きである。`LineWrap`。
   ただし `LineJisage` 1 個だけからなる行は `BlockStart`（字下げ）として複数行を開く。
7. **内容行**: 上のいずれでもない。開始も終端も内容として扱い、同一行対応が付かない
   ブロックマーカーは捨てる。

規則 4 と 5 が「終端を含む行では開始が開かない」を作る。区間の制約（制約 3）だけで解くと
開始が必ず区間を持ってしまい、ここで食い違う。

### 2. 同一行の範囲

`InlineRangeStart` と `InlineRangeEnd` は、同じ種類かつ同じ行で、深さを数えた対応を取る。
対応した区間は `Inline` または `BlockInline` に畳まれ、複数行ブロックの候補から除外する。

- 対応は同種である。
- 対応区間は交差せず、入れ子か互いに素である。
- 行途中の `Chitsuki` は対応終端が無ければ行末を仮想終端とする。
- `Warichu` は対応制約を持たず、開閉それぞれを状態なしのインラインマーカーとする。

これは現行 `find_matching_end` と `to_inlines` の役割を、`LowerPlan` より前の制約として
明示したものである。制約 1 の規則 5 が同じ行の終端を**種類を問わず**見るのに対し、
ここでの対応は同種で取る。両者が食い違うのは別種の終端が混ざる行だけで、その入力は
参照実装が停止する。

### 3. 複数行ブロックの対応と包含

制約 1 で `BlockStart` と `BlockEnd` の役割を与えられたマーカーが、ブロックの親子関係を作る。

- 開始 `s` は、`s` の後で閉じられるか EOF まで続く区間を一つ持つ。
- 終端 `e` は、`e` の直前で最も内側にある生存ブロックを、**その種類が記法に書かれた種類と
  一致するときだけ**閉じる。一致しなければ何も閉じない（参照 `check_close_match` と同じ。
  下記「規則 3 の統一」）。照合するのは最内層だけで、一致する開きを外側へ探しには行かない。
- ブロック区間は交差せず、入れ子か互いに素である。
- 複数の終端が同じ行にあれば `Position` の昇順で順に対応する。
- 閉じる相手がない終端（生存ブロックが無い、または最内層と種類が食い違う）は `IgnoredEnd`
  となり、**閉じタグを作らない**。診断 `unmatched-end` に出る。ただし行は消えず、
  その行の内容は通常の内容断片として出力される。`Break` の判定（制約 7）に入るのは
  **閉鎖に採用された終端だけ**で、採用されなかった終端は明示終端でも数えない。
  ただし行の終端が一つも採用されなかったときは、その行は内容行と同じ扱いになり、
  行内のすべての明示終端が判定に入る。
  例（いずれも実測）: 開いている字下げが 1 つのとき、`Ａ［＃字下げ終わり］Ｂ［＃ここで字下げ終わり］Ｃ`
  は裸の終端だけが採用され、残った明示終端は `Break` に効かない（`Ｃ` の後に `<br />` が出る）。
  開いているブロックが無いときの `本文［＃ここで字下げ終わり］あと` は行全体が内容行になり、
  明示終端が効いて `<br />` が出ない。

この「最も内側」は、`e` を含む生存区間のうち開始位置が最大のもの、と区間として定義する。
`solve` の `PlanStack` はこの制約を線形時間で解く実装の一つである。

終端より前にある同じ行の内容断片は、**閉じるブロックの内側**に属する。ただし閉じる相手が
ぶら下げのときだけ外側に出す（ぶら下げは行ごとに包む形なので、閉じた後の断片は包みに
入らない。実測）。

`OpenKind` は開き方から決まる。制約 1 の規則 2（単独の開始）と、規則 6 の例外
（`LineJisage` 1 個だけからなる行）は `Newline`。規則 1（ぶら下げ開始行）と規則 5
（行途中の開始）は `NoBreak` とする。

### 4. 暗黙閉じ

開始 `s` は、種別により直前の生存ブロックへ強制終端を導入する。**制約 1 の規則 1
（ぶら下げ開始行）、規則 2（単独の開始）、規則 6 の例外（`LineJisage` 1 個だけからなる
行）で開くときだけ**適用し、規則 5（行途中の開始）では適用しない。行の途中で暗黙閉じを
伴う種類を開く入力は参照実装が停止するため正解が無く、現行はそのまま入れ子にする（実測）。

`LineJisage` 単独行は `ここから字下げ` と同じ扱いで、暗黙閉じも `OpenKind::Newline` も
そのまま働く（実測: 字下げの中の `［＃４字下げ］` 単独行は `</div><div class="jisage_4">` を
出し、開始タグの後に改行が入る）。

| 新しい開始 | 強制終端の対象 | 個数 | CloseKind |
|---|---|---:|---|
| 字下げ | 最も内側の字下げまたはぶら下げ | 1 | `NoBreak` |
| 地付き | 連続する最内側の地付きまたはぶら下げ | 全て | `NoBreak` |
| ぶら下げ | 連続する最内側の字下げまたはぶら下げ | 全て | `Newline` |

強制終端は開始 `s` の直前に置かれる仮想終端である。通常の終端と同じ包含制約に参加する。
これにより「開始時にスタックを閉じる」という手順を、区間境界の制約として表せる。
`CloseKind` は上表のとおりで、制約 7 の優先順より先に決まる。

### 5. 行スコープ包み

`LineJisage` と行頭の行スコープ `Chitsuki` は、対応関係ではなく行断片への `wraps` 制約を
作る。

- 同一行の `LineJisage` は全て同じ内容断片を包む。
- 出現位置が後のものほど外側になる。
- `LineJisage` はルビ親文字の内側にあっても検出し、内容から取り除く。
- 終端を含む行の断片にも同じ `wraps` 制約が適用される（制約 1 の規則 4 に当たる行でも、
  各断片に包みが効く）。
- `LineJisage` だけからなる行は、包みではなく複数行の字下げ開始として扱う。
- `LineJisage` と行頭の行スコープ地付きが同居する行では、包むのは `LineJisage` だけとする。
  地付きは取り除かれず、行途中の地付きとして行末までを包むインラインになる。

### 6. 行結合

出力を飛ばす事実は、可変の `carry` ではなく断片間の `joins_before` 関係として表す。

- **ぶら下げ開始行**（制約 1 の規則 1。同じ行に終端マーカーが無いこと）は、開始マーカーの
  前後の内容断片を後続へ結合する。終端を含む行はこれに当たらず、結合も起こさない（実測）。
- 内容行末の `HardBreak` は、次の内容行の先頭へ結合する。
- **未結合断片は、次のぶら下げ開始行や `HardBreak` 行が来ても確定せず、累積する**。
  結合を打ち切って独立した行として確定するのは、次に来た行が内容行でも結合元でもない
  ときだけである（実測: ぶら下げ開始行が続くと、3 行が 1 つの断片列になる）。
- 行スコープ包みの `HardBreak` が次の空行を吸収する quirk は、空行を
  `suppressed_by` で表す。

結合は有向非巡回グラフであり、各断片の結合先は高々一つである。その連結成分を一つの
`Block::Line` に写す。

### 7. CloseKind と Break

`CloseKind` と `Break` は木を作る途中の副作用ではなく、確定した `LowerPlan` の属性である。

`CloseKind` は次の優先順で決まる。

1. 暗黙閉じなら制約 4 の表で決まる（字下げと地付きが起こすものは `NoBreak`、ぶら下げが
   起こすものは `Newline`）。**暗黙閉じを一律 `NoBreak` にしてはいけない**（実測）。
2. 同一行で最後ではない閉じ、または後続内容を持つ閉じなら `NoBreak`。
3. EOF で閉じるなら `Newline`。
4. それ以外で、閉じるブロックが下記のいずれかで、その親がぶら下げなら `BurasageWrapped`。
   横組み、罫囲み、キャプション、文字サイズ、太字、斜体、**字詰め、見出し**。
   字下げ、地付き、ぶら下げ自身は含まない（閉じタグが文字列としてバッファに残る種類か
   どうかで決まるので、「装飾系」という括りでは決まらない）。
5. 残りは明示終端なら `Newline`、裸の終端なら `BareBreak`。

内容断片の `Break` は、結合後のインライン列と、**結合先の行**の事実から導く。

- 明示終端を含む。判定に使うのは結合先の行のマーカーだけで、結合されてきた断片が持つ
  明示終端は数えない。
- 行末が閉じタグを出すインラインである。
- 通常見出しが入れ子を含め行内のどこかに現れる。

いずれかなら `Break::None`、それ以外なら `Break::Br` とする。行途中の前半断片
（終端より前の断片と、行途中の開始より前の断片）だけは `Break::NoNewline` とする。
制約 6 で確定した未結合断片を独立の行として出すときは、明示終端を含まないものとして扱う。

### 8. EOF と診断

EOF まで生存した開始には仮想終端を置き、`CloseKind::Newline` で閉じる。同時に
`LowerDiagnostic`（`unclosed-block`）を作る。診断は `LowerPlan` の副産物であり、AST と
レンダリング結果を変えない。

診断は 3 種ある。`unclosed-block`（EOF 閉じ残し）と `unmatched-end`（制約 3 で閉じる相手が
無い終端）は、どちらも参照が「処理を停止します」で変換を中止する入力なので Error。
`midline-block-open`（制約 1 の規則 5 で、マーカーの前に空白でない内容がある形）は参照が
受理するので Warning。**木は総関数のまま作り続ける**——エディタは入力途中の壊れた文書を
常に受け取るので、木が作れないとプレビューが丸ごと消える。厳格さは境界（CLI）が
severity を見て決める。

## 解決手順（実装を拘束しない参照形）

次の順は仕様上の依存関係であり、巨大な行ループの分岐順ではない。

1. 各行に③・③'を適用し、位置付きのマーカーと内容断片を得る。
2. コマンド候補の優先度制約を解き、各コマンドの解釈を一つに確定する。
3. 行ごとに役割の割り当て（制約 1）を解き、`MarkerFacts` を確定する。
4. 同一行範囲の対応を解き、その区間をインライン断片へ縮約する。
5. 暗黙閉じによる仮想終端を追加する。
6. 複数行ブロックの包含・終端対応を解き、ブロック森を作る。
7. 行スコープ包みと行結合を解き、各ブロックに属する内容断片を確定する。
8. `CloseKind`・`Break`・EOF 診断を導出し、`LowerPlan` を完成する。
9. `LowerPlan` を Aozora AST へ写す。

3 は行内で閉じる（行をまたぐ状態を持たない）。6 の実装に、位置順で走査するスタックを
用いてよい。ただし、同じ `MarkerFacts` と制約を与えれば、別実装（区間グラフや
ワークリスト）でも同じ `LowerPlan` になることを要件とする。

## LowerPlan

`LowerPlan` は公開交換形式ではなく、Lowerer 内部の解決済みモデルである。

```rust
struct LowerPlan {
    roots: Vec<PlanBlock>,
    joins: Vec<Join>,
    suppressed_lines: Vec<usize>,
    diagnostics: Vec<LowerDiagnostic>,
}

enum PlanBlock {
    Content(PlanLine),
    Nested {
        kind: BlockKind,
        open: OpenKind,
        close: CloseKind,
        opened_at: Position,
        closed_by: Closure,
        children: Vec<PlanBlock>,
    },
    LineWrap {
        kinds: Vec<BlockKind>,
        line: PlanLine,
    },
}

struct PlanLine {
    fragments: Vec<ContentFragment>,
    break_kind: Break,
    source_lines: Vec<usize>,
}

enum Closure {
    Explicit(FactId),
    Bare(FactId),
    Implicit { caused_by: FactId },
    Eof,
}
```

`closed_by` と `source_lines` は、現行 AST に無い説明用の情報である。初期導入では内部だけに
留め、AST化の際には捨ててよい。これにより「なぜこのブロックがここで閉じたか」を
診断・テスト失敗・デバッグ表示で追跡できる。

## 互換性の不変条件

プロファイルを 3 つに分ける。**AST の等価性を課すのは現行再現プロファイルだけ**である。
既知バグの修正と解決器の入れ替えを同じプロファイルに入れると、等価性の要求と修正方針が
両立しない。

| プロファイル | 何に一致させるか | どう測るか |
|---|---|---|
| 現行再現 | 現行 `lower_to_blocks` の出力（既知バグを含めてそのまま） | 現行実装との並走で AST と診断を比較 |
| 参照互換 | 参照実装 aozora2html の出力 | コーパスとの byte 一致（悪化 0） |
| 将来 | 設計として正しい意味論 | 対象を決めたうえで個別に定める |

現行再現プロファイルでは、同じ `RawDoc` に対して次を満たさなければならない。

1. `materialize(solve(raw))` は現行 `lower_to_blocks(raw)` と同じ Aozora AST を返す。
2. `solve_with_diagnostics(raw)` の診断列は現行
   `lower_to_blocks_with_diagnostics(raw)` と同じになる。
3. HTML レンダラの出力は既存のオラクルとの byte 一致を保つ。
4. 解決器の走査方法を変えても `LowerPlan` が不変である。

これが**移行そのものの受け入れ基準**である。解決器を入れ替える変更では出力を 1 バイトも
変えない。現行実装が「参照実装が停止するため正解が無い」としている入力域も、
**現行の全域的フォールバックをそのまま制約として採用する**。制約 1 の規則 3 はこの入力域に
属する非対称であり、整理したくなるがここでは触らない。

現行再現と参照互換が食い違うのは、次節に挙げた既知の非互換の入力だけである。その修正は
**移行が終わってから、独立した変更として**行った（規則 5。2026-08-03）。該当入力の
AST は移行前の実装と変わるので、不変条件 1 の対象外である。

不変条件 4 を満たすには、現行が可変状態で表している次の 3 つを関係として持つ必要がある。
初稿ではいずれも制約が緩く、走査順を変えると結果が変わった。

- 開いているブロックの並び。制約 3 の区間の包含として表す。
- 未結合断片の持ち越し。制約 6 の `joins_before` として表す。累積するので、断片から
  断片への関係であって、行から行への関係ではない。
- 吸収した行。`suppressed_by` として表す。

## 既知の非互換と将来の統一

制約 1 の規則 3 と規則 5 は、どちらも「ブロックの開閉が種類と噛み合わない入力」を扱う
規則だが、参照実装に正解があるかどうかが違う。どちらも 2026-08-03 に片づけた——規則 5 は
正解があったので参照に合わせ、規則 3 は正解が無いので**設計として**最内層照合へ統一した。

### 規則 5 の互換バグ（2026-08-03 に直した）

参照はマーカーの前に何があってもブロックを開くのに、こちらは「前がすべてテキスト」の
ときだけ開いていた。2026-08-03 に参照実装で 5 形を実測し、ガードを落とした。

| 開始マーカーの前 | 参照 | 修正前 | 修正後 |
|---|---|---|---|
| テキストのみ | `本文<div class="shatai">つづき…` | 一致 | 一致 |
| ルビ | `<ruby>…</ruby><div class="shatai">つづき…` | div が出ない | 一致 |
| 外字 | `…class="gaiji" /><div class="shatai">…` | div が出ない | 一致 |
| 傍点（前方参照） | `<em class="sesame_dot">本文</em><div class="shatai">…` | div が出ない | 一致 |
| 行内の地付き | `…<div class="chitsuki_0">本文<div class="shatai">つづき</div>` | div が出ない | div は出るが入れ子が違う |

参照は 5 件とも正常終了するので、これは正解のある差だった。失敗の仕方も悪く、開始が
黙って消えて書式が丸ごと落ちるうえ、対応する `［＃ここで…終わり］` が別のブロックを
閉じにいくので誤りが伝播していた。

`head_is_text` は意味のある規則ではなく、この経路を導入したときに影響範囲を絞るための
保守的なガードだった（実装でこの条件にだけ根拠コメントが無く、引用されていた実文書 2 件は
どちらも前が空白テキストである）。**条件を落とすだけで済んだ。** 「行途中では暗黙閉じを
しない」（制約 4）は独立の規則なのでそのまま残る。

最後の 1 形（行内地付きの後で開く）だけ範囲が参照と違う。**これは追随しない**。
根拠は次項にまとめる。

オラクルは 1 件も動かなかった（悪化 0・改善 0・全 17509 件の判定が前後で完全一致）。
この形が書庫の文書に現れないことの確認でもある。5 形は `lower/solve.rs` の
`mid_line_open_ignores_what_precedes_the_marker` に実測値として固定してある。

### 行中の `ここから…` に追随しない範囲（2026-08-03 に決めた）

`前［＃地付き］本文［＃ここから斜体］つづき` / `次行` / `［＃ここで斜体終わり］` で、
参照とこちらは**範囲が入れ替わる**。

| | 地付きの範囲 | 斜体の範囲 |
|---|---|---|
| 参照 | 2 行（斜体終わりの行まで） | 1 行目だけ |
| こちら | 1 行目だけ | 斜体終わりの行まで |

記法の定義（`［＃地付き］` は行スコープ、`ここから…ここで終わり` は行をまたぐ範囲）に
沿っているのは**こちら**である。参照は両者を取り違えている。参照自身の状態も出力と
食い違っていて、`［＃ここで斜体終わり］` は受理するのに `［＃ここで地付き終わり］` は
「地付き中ではありません」で拒否する（実測）。つまり内部では斜体が開いていることに
なっているのに、出力では斜体の `</div>` が 1 行目で閉じている。

追随しない理由は 3 つ。

1. **参照の挙動が一貫していない。** 再現するには「`斜体終わり` で地付きを閉じる」ことに
   なり、制約 3 の最内層照合（今まさに参照 `check_close_match` に合わせた規則）に
   例外を彫り込むことになる。
2. **HTML では両方とも記法の見た目にならない。** `.shatai` に `display` の指定は無く
   `div.shatai` はブロック要素なので、行中で開くと**必ず行が割れる**。もとの入力では
   `本文` と `つづき` は同じ行だが、参照でもこちらでも別の行になる。参照に合わせても
   意図に近づかず、別の壊れ方に乗り換えるだけである。
3. **書庫に無い。** オラクル 17509 件の判定が前後で完全一致。

代わりに、この形には診断 `midline-block-open`（Warning）を出す。注記一覧には行中の
`ここから…` の例が無い（全例・記入例とも 46 箇所すべて行頭。実測）。参照は字下げ以外を
受理する（字下げだけ nil を踏んでクラッシュする）ので Error にはしない。

診断の対象は**マーカーの前に空白でない内容がある**形だけにする。開始タグの直後から本文が
始まる形（前が空か全角空白だけ）は実文書にあり（001065/18361 の
`　［＃ここから斜体］Fourscore…`、001841/57318 の `［＃ここからキャプション］図３…`）、
行も割れないので対象外である。

### 規則 3 の統一（2026-08-03 に入れた）

参照は該当する入力すべてで停止する（縦中横、傍点、割書、注記付き終わり、裸の太字終わり。
いずれも実測）。加えて**種類が食い違う終端そのもの**が停止する。

```
［＃ここから太字］/ 本文 / ［＃ここで字下げ終わり］   → 参照は停止（設計された拒否）
```

つまり以前の制約 3「記法に書かれた種類を対応の制約に使わない」は、型が一致する正常な
文書でしか検証されていなかった。型が食い違う領域は設計の自由があるので、`written_kind` を
使って規則 3 と規則 4 を一つにした。

> 終端は、**最も内側の生存ブロックの種類が記法に書かれた種類と一致するときだけ**閉じる。
> 一致しなければ何も閉じず、マーカーを捨てて診断（`unmatched-end`）に出す。

照合するのは**最内層だけ**である。「一致する最も内側のブロック」を探しにいく形にしては
いけない。内側の異種ブロックを飛び越して外側を閉じることになり、制約 3 の「ブロック区間は
交差せず、入れ子か互いに素である」が破れる。最内層だけを見れば、閉じるのは常に最内層か、
さもなくば何も閉じないので、入れ子は保たれる。

型が一致する正常文書では以前と同一の結果になり（オラクル 17509 件の判定が前後で完全一致）、
`block_kind_of` が写せない種類は最内層に来ることが無いので、ガードを別に書かなくても
閉じなくなった。非対称が規則としてではなく帰結として消え、誤り回復も局所的になった。
無関係なブロックを閉じるのは誤りを文書の遠くへ伝播させるが、閉じ残しなら内容は失われず
`unclosed-block`/`unmatched-end` で見える。

実文書で `unmatched-end` が出るのは 13 箇所 / 7 文書で、いずれも**原文側の記法ミス**である
（例: 000106/2415 の `[＃数字は１字下げ…` は始まりが半角 `[` なので、対応する
`［＃ここで字下げ終わり］` が宙に浮く）。7 文書とも HTML はオラクルと `exact` のままで、
出力を変えずに欠陥だけが見えるようになった。

**`written_kind` の正準化はしない。** この規則へ移すと裸の `［＃太字終わり］` が
`ここから太字` を閉じなくなる。開始 `［＃ここから太字］` は `Futoji`、裸の終端は `Style` と、
同じ「太字」が別の種類に落ちるためである（終端側が `StyleType` を先に見る。
[spec-commands.md](spec-commands.md) の分岐 10）。**参照はこの形で NoMethodError で
クラッシュする**（設計された拒否ではない。実測）ので正解が無く、書庫にも組み合わせが
無い（裸の `［＃太字終わり］`/`［＃斜体終わり］` は 4691 箇所 / 97 文書あるが、すべて
同一行で開閉する範囲形で `to_inlines` が畳む）。閉じずに `unmatched-end` を出す側で
確定した。正準化は同一行範囲の対応づけ（`find_matching_end` は `block_type` 同種で取る）へ
波及するので、得るものに比べて高い。

## 移行の記録と残り

1. ✅ 旧行ループを逐語コピーして凍結し、テストとコーパス規模の example で並走させた。
   **並走検証を最初に用意した**のが効いた——本書の改訂で潰した 7 件の非互換は、いずれも
   並走で機械的に検出できる種類のもので、制約の読み合わせだけでは見落とす。
2. ✅ 役割の割り当て（制約 1）→ `LowerPlan` と materialize → 暗黙閉じ（制約 4）→
   行結合（制約 6）→ 閉じの導出（制約 7）の順に移した。各段で全書庫並走を通した。
3. ✅ 解決器を既定経路にし、凍結コピーと並走検証を削除した。
4. ✅ コマンド振り分けを候補＋優先度表（`DISPATCH`）へ移し、優先順位をテスト可能な
   データにした（②の話で Lowerer とは独立）。
5. ✅ 既知の非互換（規則 5 の `head_is_text`）を独立した変更として直した。

**1 から 4 は現行再現プロファイルの中に収まり、出力を 1 バイトも変えない。** 参照互換への
移動は 5 だけで、そこはオラクルの悪化 0 で測る。両者を混ぜると、並走検証の
「完全一致」が使えなくなる。
