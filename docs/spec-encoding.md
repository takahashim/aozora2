# 文字コードの仕様

改訂: 2026-07

青空文庫形式の処理における文字コードの扱いを定める。バイト列と内部表現の境界、
および JIS にない文字（外字）の扱いが対象。

読者は本実装の保守者と、他言語への移植者。移植者が Shift_JIS の符号化器を持たない
環境でも再現できるよう、判断に必要な表と規則は「どこに何があるか」まで書く。

---

## 1. 対象と前提

### 1.1 何を前提にしているか

- 青空文庫の公開テキストファイルは **Shift_JIS ＋ CRLF** のプレーンテキスト。
- 本実装の内部表現は **UTF-8 の `String`**、位置は **char 単位**（バイト単位ではない）。
- 参照実装 aozora2html（Ruby）は Shift_JIS のまま処理するため、文字コードに起因する
  挙動の差が生まれうる。差が出る箇所は本書で明示する。
- 「文字コード」と「記法」は分けて扱う。`※［＃…］` の**構文**は
  [spec-tokenizer.md](spec-tokenizer.md) が定め、本書は「その記法で表される文字を
  どう解決し、どう出力するか」を定める。

### 1.2 位置の数え方

- 内部の位置（`Span`、`analysis` の診断・トークン）は **0 起点の行番号と char 桁**。
- バイト位置は使わない。エディタ（CodeMirror）や LSP が char 単位で位置を扱うため。
- 利用者に見せるとき（エラーメッセージ等）だけ 1 起点に直す。

## 2. 入口と出口

### 2.1 読み込み（バイト列 → 内部表現）

- `encoding::decode_to_utf8` が判定する。順序は次のとおり。
  1. UTF-8 BOM（`EF BB BF`）があれば剥がして UTF-8 として読む。
  2. UTF-8 として妥当なら UTF-8。
  3. それ以外は Shift_JIS。
- この順序には限界がある。Shift_JIS のバイト列がたまたま UTF-8 として妥当になる場合は
  UTF-8 と誤判定する。実運用のコーパスでは問題になっていないが、あくまで判定は**発見的**である。

### 2.2 改行

- 行の区切りは **CRLF のみ**。単独の LF や CR は本文の文字として扱う
  （参照実装 Jstream が CRLF だけを改行と見るため）。
- エディタ（CodeMirror）の内容は LF なので、境界で CRLF に正規化する。
  - `html::convert_editor` … プレビュー変換の入口。CRLF に直してから `convert` を呼ぶ。
    直さないと全文が 1 行と見なされ、ヘッダ抽出が全文をタイトル化して本文が空になる。
  - `save_shift_jis`（GUI） … Shift_JIS 保存の入口。同じ正規化を行う。本文テキストと
    変換後の HTML の両方がここを通る（HTML は既に CRLF なので素通しになる）。

### 2.3 書き出し（内部表現 → バイト列）

| 出口 | 実装 | 現状 |
|---|---|---|
| HTML（CLI） | `aozora2 html --encoding` | `shift_jis`（既定）と `utf-8` を選べる |
| HTML（GUI） | `save_shift_jis` | Shift_JIS ＋ CRLF |
| テキスト（GUI） | `save_shift_jis` | Shift_JIS ＋ CRLF |
| テキスト（GUI・UTF-8） | `writeTextFile` | UTF-8。「テキストを保存」はこちら |
| プレビュー（GUI） | webview に直接渡す | UTF-8（ファイルにしない） |

- 書き出しの手順は Shift_JIS のどの出口でも同じ。**改行を CRLF に正規化 → 符号位置を
  正規化（[3.2](#32-復号は一意符号化は全射でない)）→ 直接書ける文字か検査
  （[3.3](#33-直接書ける文字ascii--jis-x-0208)）→ 符号化**。
- GUI の HTML 保存は以前 UTF-8 で書いていた。宣言（次節）は Shift_JIS 固定なので、
  宣言と実バイト列が食い違っていた。プレビューは iframe の `srcdoc` で親文書の UTF-8 を
  継ぐため正しく見え、保存したファイルを外で開くまで露見しなかった。

### 2.4 HTML の出力エンコーディング（未整備）

- 現状、HTML の**宣言は Shift_JIS 固定**である。`document_renderer::render_html_head` が
  次の 2 行をハードコードしている。

  ```
  <?xml version="1.0" encoding="Shift_JIS"?>
  <meta http-equiv="Content-Type" content="text/html;charset=Shift_JIS" />
  ```

- したがって `aozora2 html --encoding utf-8` は、**UTF-8 のバイト列に Shift_JIS の宣言**が
  付いた不整合な HTML を出す。既定（`shift_jis`）では一致するので露見しない。
- 両対応にするなら、出力エンコーディングを `RenderOptions` に持たせ、宣言と実バイト列の
  両方をそこから決める。決めるべき点は次の 3 つ。
  - **既定は Shift_JIS のまま**にする（公開ファイルとのバイト一致を守るため）。
  - UTF-8 出力では BOM を付けない（XHTML の宣言で足りる）。
  - UTF-8 出力なら外字を数値文字参照で出せる幅が広がる（[5.4](#54-出力の三経路)）。
    ただし既定の外字画像はバイト一致の要なので、既定は変えない。

## 3. 符号化の仕様

### 3.1 変換器と、参照実装との違い

- 本実装は符号化・復号ともに **`encoding_rs`（WHATWG Encoding Standard の shift_jis）** を
  使う。WHATWG の索引は曖昧な符号位置を **Windows-31J（CP932）寄せ**で定める。
- 参照実装 aozora2html は Ruby の **`Encoding::Shift_JIS`**（JIS X 0208 ＋ X 0201 の対応、
  ベンダ拡張なし）で書き出す（`lib/output_stream.rb`）。読み込みは
  `File.open(input, 'rb:Shift_JIS')`（`lib/aozora2html.rb`）。
- **両者の対応表は一部が鏡像になっている**。実測値は次のとおり。

  | | Ruby `Shift_JIS`（参照実装） | encoding_rs（本実装） |
  |---|---|---|
  | `81 60` の復号 | U+301C 〜 | U+FF5E ～ |
  | U+301C の符号化 | `81 60` | 不可 |
  | U+FF5E の符号化 | 不可 | `81 60` |
  | U+2014 の符号化 | `81 5C` | 不可 |
  | U+2015 の符号化 | `81 5C` | `81 5C` |

- 内部表現はどちらも UTF-8 である。参照実装も `Jstream` が読み込み時に UTF-8 へ変換し、
  `TagParser` は UTF-8 以外を受け付けない。Shift_JIS はどちらも入口と出口にしかない。
- **移植する場合の不変条件は「復号と符号化で同じ表を使うこと」**。どちらの表を選んでも
  バイト境界では等価になる（下記）。表の選択が効くのは、外から来た UTF-8 テキストを
  符号化するときに正規化がどちら向きになるか、だけである。

### 3.2 復号は一意、符号化は全射でない

- 復号（Shift_JIS → Unicode）は一意に決まる。
- 符号化（Unicode → Shift_JIS）は**全射ではない**。同じ文字を表す Unicode 符号位置が
  複数あり、選んだ表が対応づけているのは片方だけ、という組があるため。
- `encoding_rs` で符号化できない側と、その寄せ先（実測値）。

  | 符号化できない符号位置 | 寄せ先 | Shift_JIS | 備考 |
  |---|---|---|---|
  | U+301C 〜 波ダッシュ | U+FF5E ～ 全角チルダ | `81 60` | macOS の日本語入力は左を作る |
  | U+2014 — EM DASH | U+2015 ― 水平線 | `81 5C` | 「──」の入力で紛れる |
  | U+2016 ‖ 双柱 | U+2225 ∥ 平行記号 | `81 61` | |
  | U+00A2 ¢ | U+FFE0 ￠ | `81 91` | |
  | U+00A3 £ | U+FFE1 ￡ | `81 92` | |
  | U+00AC ¬ | U+FFE2 ￢ | `81 CA` | |

- 6 組は [3.1](#31-変換器と参照実装との違い) の鏡像そのもの。参照実装ではこの表の
  **左側が符号化でき、右側ができない**。
- U+2212（−）と U+FF0D（－）はどちらも `81 7C` に符号化できる（復号は U+FF0D）。
  符号化時に困らないので対応表には含めない。

### 3.3 直接書ける文字（ASCII ＋ JIS X 0208）

- 青空文庫形式は **JIS X 0208 を前提**とし、その外の文字は外字注記 `※［＃…］` で書く。
  したがって「Shift_JIS のバイト列にできるか」ではなく「**X 0208 の内か**」で判定する。
  この 2 つは一致しない。
- `encoding::is_directly_writable` が判定する。ASCII は許し、それ以外は符号化して
  **区**を見る。X 0208 は面 1 の**区 1〜8**（記号・英数・かな・ギリシャ・キリル・罫線）
  ＋**区 16〜84**（第 1・第 2 水準漢字）で、CP932 の拡張はいずれもこの外に置かれている
  ため、区の範囲だけで分離できる（対応表を別に持つ必要がない）。
- 拒否するもの。

  | 種類 | 例 | 区 | CP932 で符号化 |
  |---|---|---|---|
  | NEC 特殊文字 | ① Ⅰ ㈱ ㎜ | 区 13 | できる |
  | NEC 選定 IBM 拡張 | | 区 89〜92 | できる |
  | IBM 拡張 | 﨑 | 区 115〜119 | できる |
  | JIS X 0201 | 半角カナ、`¥` U+00A5、`‾` U+203E | — | できる（1 バイト） |
  | JIS X 0213 の追加分 | 睜（第 3 水準）、𥥔（第 4 水準）、ヷ | — | できない |
  | その他 | 絵文字、é ü æ | — | できない |

- **参照実装と同じ線引きになっている**ことを、BMP 全域（65,536 文字）で Ruby の
  `Encoding::Shift_JIS` と突き合わせて確認した。受理集合は双方 **7,008 字**で一致し、
  差は [3.2](#32-復号は一意符号化は全射でない) の 6 組（同じバイトを指す綴り違い）だけ。
  保存時は正規化を先に通すので、どちらの綴りでも受け付ける。

### 3.4 符号化できない文字はエラーにする

- `encoding_rs` の `encode()` は WHATWG 仕様（フォーム送信用）に従い、符号化できない
  文字を**数値文字参照の文字列**に置き換える。`〜` は `&#12316;` という 8 文字の ASCII に
  なる。`?` や `〓` と違い、壊れたことに気づきにくい。
- 本実装はこれに頼らない。`encoding::encode_shift_jis` は**符号化の前に全文を検査**し、
  直接書けない文字が 1 つでもあれば行・桁つきのエラーを返して**保存しない**。
- 根拠は青空文庫形式のルールである。X 0208 の外の文字が直接書かれている状態は入力の
  誤りであり、黙って置き換えてよい場面ではない。参照実装も符号化に失敗すれば例外で
  止まる（NBSP だけは `&nbsp;` に逃がす特例がある）。
- 検査を通った文字列は必ず符号化できるので、`had_errors` は `debug_assert!` の保険。

### 3.5 既知の穴

- CLI の `--encoding shift_jis` は `SHIFT_JIS.encode()` の `had_errors` を捨てている
  （`crates/aozora2/src/commands/html.rs`）。数値文字参照への置き換えが黙って起きうる。
  HTML には定型文も含まれるため、エラーで止めるか警告に留めるかは未決。
- HTML の宣言が Shift_JIS 固定である（[2.4](#24-html-の出力エンコーディング未整備)）。

### 3.6 復号 → 符号化が恒等になる条件

- **入力が Shift_JIS のときだけ**。その場合は自分の表で往復するので、内部の符号位置が
  参照実装と違っても、書き出したバイト列は一致する。

  ```
  参照実装:  81 60 → U+301C → 81 60
  本実装:    81 60 → U+FF5E → 81 60
  ```

- **入力が UTF-8 のときは成り立たない**。X 0208 の外の文字を直接書けてしまうため。
  手元の `koku.txt`（UTF-8）では 134 箇所が該当した（第 3・第 4 水準の漢字、ラテン文字
  `é ü æ`、記号 `⁉‼ℵ½¾`、`ヷ` など）。青空文庫形式としては外字注記で書くべき箇所である。
- この非対称性は検証の設計に影響する（[8 章](#8-テストで縛っていること)）。

## 4. 文字集合と変換表

### 4.1 表を外部データに置く理由

- 表は `crates/aozora-core/data/` に JSON/TSV で置き、`build.rs` がコンパイル時に
  Rust の表へ変換する。コード中に定数として埋めない。
- 理由は 2 つ。
  - **移植可能性**: 他言語の実装者が Shift_JIS の対応表や `encoding_rs` 相当を持たなくても、
    このデータだけで判定を再現できる。
  - **検算可能性**: 一次データが目で読める形にあるので、境界や多対一の対応を確認できる。
    生成時に自己整合性を検査し、崩れていればビルドを止める。

### 4.2 データ一覧

| ファイル | 内容 | 使う場所 |
|---|---|---|
| `jis2ucs.json` | JIS X 0213 の面区点 → Unicode | `jis_table`・外字・アクセント・`jis_x0208` の生成 |
| `accent_table.json` | アクセント記法 → 面区点と説明 | `accent` |
| `original_title_chars.json` | 原題（欧文表題）と見なす文字 274 字 | `document` のヘッダ解釈 |
| `command_table.tsv` | 参照実装の記法表スナップショット | `html::presentation` の照合テスト |

### 4.3 面区点コードの書式

- 書式は `面-区-点`（例 `1-02-22`、`2-14-75`）。面は 1 か 2。
- 区・点は 1〜2 桁で書かれうるので、表を引く前に `jis_table::normalize_jis_code` が
  **2 桁ゼロ詰め**に正規化する（`1-2-22` → `1-02-22`）。
- `jis2ucs.json` の値は数値文字参照の文字列（`"&#x3000;"`）。合成文字は複数個並ぶ
  （例 `1-05-87` = カ + 半濁点）。

### 4.4 JIS X 0208 の漢字判定

- ルビ親文字の文字種判定（[6 章](#6-文字種の判定)）が「この字は漢字か」を問う。
- 対象は JIS X 0208 の漢字 6,355 字（第 1 水準 2,965＋第 2 水準 3,390）。
- Unicode 上では 4,031 本のレンジに散らばるためレンジ列挙できないが、**区点空間では
  面 1 の 16-01〜47-51 と 48-01〜84-06 の 2 レンジ**で表せる。`build.rs` はこの 2 レンジを
  `jis2ucs.json` から引いてビットマップを生成する（`jis_x0208`）。判定は O(1)。
- 移植時もこの 2 レンジを使えば、符号化器なしで同じ集合を作れる。
- これは**漢字だけ**の集合であることに注意する。「本文に直接書けるか」（X 0208 全域）の
  判定は別で、そちらは区の範囲で見る（[3.3](#33-直接書ける文字ascii--jis-x-0208)）。
  前者はルビ親文字の連なり判定、後者は保存時の検査に使う。

### 4.5 原題判定の文字集合

- 参照実装は Shift_JIS のバイト値の範囲でヘッダ行を判定している。`original_title_chars.json`
  は**同じ集合を Unicode で書き出したもの**なので、対応表を持たない実装でも再現できる。
- 収録は 274 字。ASCII（U+0000-U+007F）＋区点 1-01-01〜1-03-25（記号・全角数字）＋
  1-06-01〜1-07-81（ギリシャ・キリル）。
- Shift_JIS の 1 バイト文字である `¥`（U+00A5）と `‾`（U+203E）は区点を持たないため
  `kuten` が `null`。

### 4.6 表によって対応の由来が違う

- **同じ区点でも、表によって対応先の Unicode 符号位置が違う**。由来が異なるため。

  | 区点 | `jis2ucs.json` | `original_title_chars.json` |
  |---|---|---|
  | 1-01-33 | U+301C 〜（JIS X 0213 本来の対応） | U+FF5E ～（WHATWG 由来） |

- `jis2ucs.json` は JIS X 0213 の規格どおりの対応、`original_title_chars.json` は
  参照実装の判定（Shift_JIS のバイト範囲）を WHATWG の復号で写したもの。
- 実害は出ていない。前者を引くのは外字の解決で、その結果は数値文字参照か画像になり、
  Shift_JIS の符号化器を通らないため。後者は集合の所属判定にしか使わない。
- ただし**表を混ぜて使うと壊れる**。新しい用途で表を引くときは、その用途が「規格どおりの
  対応」を要るのか「参照実装が実際に見ている文字」を要るのかを確かめること。

## 5. 外字（JIS にない文字）

### 5.1 記法と解決の優先順位

- 記法は `※［＃説明、面区点］` または `※［＃説明、U+XXXX］`（`＃` は省略されうる）。
- 解決は次の順（参照実装 `dispatch_gaiji` と同じ）。
  1. **面区点コード**を探す。取れれば、変換表にあれば Unicode、なければ画像。
  2. 取れなければ **U+ 指定**を使う。
  3. どちらも無ければ変換不能として注記のまま出す。
- U+ と面区点の両方がある説明（`「りっしんべん＋粟」、U+619F、2-12-34`）は**面区点が優先**。

### 5.2 面区点コードの制約

- 参照実装 `kuten2png` は `[12]-\d{1,2}-\d{1,2}` にしか一致させない。面は **1 桁の 1 か 2**、
  区・点は 1〜2 桁。
- したがって `24-1-3`（底本の位置参照であって面区点ではない）や `第4水準` の 4 は
  一致せず、画像化されない。
- 2 つのガードがある。どちらかに当たれば面区点として扱わない。
  - 説明に `非0213外字` を含む … つくりの水準参照があっても画像化しない。
  - 説明が `※.*※` に一致する … `※` が 2 つ以上ある説明は画像化しない。

### 5.3 説明文の構造

- 外字一覧（「表記について」）に出す名前と出現位置は、説明の**最後の `、`** で割る。
  前が外字名、後ろが「ページ-行」。
- `＃` の無い `※［...］` は参照実装の `PAT_GAIJI` が一致しないため、外字名も出現位置も
  空になる。この差は `had_igeta` フラグで持ち回る。

### 5.4 出力の三経路

| 経路 | 条件 | 出力 |
|---|---|---|
| 外字画像 | 面区点があり、数値文字参照を使わない設定 | `<img src=".../1-85-57.png" class="gaiji" />` |
| 数値文字参照 | `use_jisx0213`（JIS X 0213 の文字）／`use_unicode`（U+ 指定） | `&#33256;` の形 |
| 注記のまま | 変換不能 | `※<span class="notes">［＃…］</span>` ＋ 外字一覧に載せる |

- 既定は画像。公開ファイルとバイト一致させるため。
- GUI のプレビューは `use_unicode` を立てる。画像取得が減って軽くなる。
- 注記のままの `※` は**本文でだけ**付く。奥付など tail セクションでは付かない
  （参照実装 `tail_output` が付けないため）。

### 5.5 外字に準じる記法

- **アクセント分解** `〔A^〕` … `accent_table.json` で面区点に解決し、外字と同じ経路で出す。
  参照実装のアクセント表には字母が落ちた説明があり、既定では再現する（Quirk
  `accent_name_typos`）。
- **濁点付き片仮名** … 面区点 1-7-82〜85 に対応する 4 文字を直接出す。
- **くの字点** `／＼`・`／″＼` … 文字ではなく表記だが、使用の有無を「表記について」に
  出す必要があるため、生のソース行を走査して数える（注記の中に書かれることがあるので、
  パース後ではなく生の行を見る）。

## 6. 文字種の判定

- ルビの親文字を自動抽出するとき、どこまでを親文字とするかを文字種で決める
  （`char_type`）。参照実装の正規表現に対応する。

| 種別 | 範囲 |
|---|---|
| ひらがな | ぁ-ん（U+3041-U+3093）、ゝゞ |
| カタカナ | ァ-ン（U+30A1-U+30F3）、ー、ヽヾ、ヴ |
| 全角 | ０-９・Ａ-Ｚ・ａ-ｚ、ギリシャ、キリル、記号（−＆'，．） |
| 半角 | A-Z・a-z・0-9、`# - & ' ,` |
| 漢字 | JIS X 0208 の漢字 6,355 字 ＋ 々 ※ 仝 〆 〇 ヶ |
| 半角終端 | `. ; " ? ! )` |

- 漢字の追加 6 字は参照実装 `[亜-熙々※仝〆〇ヶ]` に対応する。青空文庫作業マニュアルが
  「`｜` がいるかいらないかの判断にあたっては漢字とみなす」と規定している
  （`※` のみマニュアル未記載だが参照実装にある）。
- **X 0208 の外**（NEC/IBM 拡張漢字、X 0213 の第 3・第 4 水準）は漢字と見なさない。
  参照実装では `:else` になり、ルビ親文字の連なりがそこで切れる（例: 厓 = U+5393）。
- 半角終端記号は、直前が半角のときだけ同じグループに入る（`Fig.《…》` の親文字は `Fig.`）。

## 7. 落とし穴

- **macOS の日本語入力**は「〜」を U+301C、「—」を U+2014 で入れる。青空文庫のファイルを
  読み込んだ部分は U+FF5E / U+2015 なので、**手入力した箇所だけ**符号化できない、という
  混ざり方をする。保存時の正規化（[3.2](#32-復号は一意符号化は全射でない)）が吸収する。
- **正規化は同じ文字の符号位置違いだけ**に留める。絵文字や JIS 外の漢字を `〓` などに
  寄せると、外字注記で書くべき箇所が黙って潰れる。
- **「Shift_JIS にできる」と「直接書いてよい」は違う**。CP932 は ①﨑㎜ を符号化できるが
  X 0208 の外なので、青空文庫形式では外字注記で書く（[3.3](#33-直接書ける文字ascii--jis-x-0208)）。
- **UTF-8 のファイルは X 0208 の外の文字を持ちうる**。読み込めても保存できない、という
  非対称が起きる（[3.6](#36-復号--符号化が恒等になる条件)）。
- **UTF-8 出力の宣言不整合**（[2.4](#24-html-の出力エンコーディング未整備)）。
- **CLI の `had_errors` 握り潰し**（[3.5](#35-既知の穴)）。

## 8. テストで縛っていること

- **対応表の前提**: [3.2](#32-復号は一意符号化は全射でない) の各行について「左は符号化
  できない・右はできる・正規化で左が右になる」を検査する。`encoding_rs` 側の索引が
  変われば落ちる。
- **直接書ける文字の線引き**: ASCII と X 0208 を受け、CP932 拡張・X 0201・X 0213 追加分を
  拒否すること。参照実装との一致は BMP 全域で照合済み
  （[3.3](#33-直接書ける文字ascii--jis-x-0208)。手作業の照合で、常設テストではない）。
- **検査の失敗報告**: 直接書けない文字が、数値文字参照に化けず位置つきで返ること。
- **記法表の drift 検出**: `command_table.tsv` と CSS クラス・HTML 要素の対応を照合する。
  参照実装が表を更新したらスナップショットを取り直し、この照合で差分を検出する。
- **原題文字表の自己整合性**: `original_title_chars.json` の `char` 列・`kuten` 列が
  符号位置と食い違う場合、あるいは宣言した区点レンジの外に出た場合、ビルドを止める。
- **JIS X 0208 判定の等価性**: 生成したビットマップと区点レンジからの導出が BMP 全域で
  一致すること。

### 8.1 「バイト一致」は Shift_JIS のバイト列で定義する

- **定義**: 参照実装 aozora2html が書き出す **Shift_JIS のバイト列**と、本実装が Shift_JIS で
  書き出すバイト列が 1 バイトも違わないこと。基準は常に Shift_JIS のバイト列である。
- 内部表現（UTF-8 の符号位置）では定義しない。両実装の対応表は一部が鏡像で
  （[3.1](#31-変換器と参照実装との違い)）、`81 60` を参照実装は U+301C、本実装は U+FF5E として
  持つ。内部表現で定義すると、正しく動いていても一致しえない。青空文庫が公開するのは
  Shift_JIS のファイルなので、その水準で定義するのが実態に合う。
- **検査は定義どおり行っている**（2026-07-30 実測で確認）。
  - オラクルハーネス `aozora-htmlcheck` は、`html::convert` の返り値を `SHIFT_JIS.encode`
    で符号化し直し、オラクル（gzip を展開した Shift_JIS の生バイト列）と `==` で
    突き合わせる（`src/main.rs` の `byte_equal`）。UTF-8 同士の比較ではない。
  - `crates/aozora2/tests/compatibility_test.rs` も同じ水準に揃えた。期待値ファイルの
    バイト列と、変換結果を Shift_JIS に符号化したバイト列を直接比べる。
  - 効いていることは実測で裏が取れている。`exact` 判定 400 件を変換し直すと全件が
    バイト一致で再現し、**そのうち 45 件（11%）は cp932 表と shift_jis 表のどちらで
    復号するかで UTF-8 表現が食い違う**。内部表現で定義していたら、正しく動いていても
    一致しえなかった一群である。
- ただし入力が Shift_JIS である範囲に限る（[3.6](#36-復号--符号化が恒等になる条件)）。
  入力が UTF-8 のときは復号→符号化が恒等にならずバイト比較は正当に失敗しうるので、
  `compatibility_test.rs` はその場合だけ UTF-8 同士の比較に落とす。
- 符号化器の挙動（`had_errors`。[3.5](#35-既知の穴)）については、バイトで比べる以上
  **偽の一致は起きない**（置換が起きればバイト列が変わり `different` になる）。
  ただしハーネスは `had_errors` を捨てるので、不一致の原因が符号化器かどうかの
  切り分けはできない。`compatibility_test.rs` は `had_errors` を assert して切り分ける。
- 次の層は依然として**オラクルの外**であり、別に不変条件として書く必要がある。
  - 出力エンコーディングの選択と、宣言との整合（[2.4](#24-html-の出力エンコーディング未整備)）。
    ハーネスは常に Shift_JIS で符号化するので、CLI の `--encoding utf-8` 経路は通らない。
  - ファイル書き出しの経路。GUI の保存（`save_shift_jis`）と CLI の `--charset` は
    オラクルの対象外。
