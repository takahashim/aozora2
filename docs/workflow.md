# 作業の進め方

改訂: 2026-07

aozora2 の保守・開発の作業手順を定める。以後の作業は本書に従う。

手順は原則（docs/architecture.md 1 章: 荷重原則・誘因整合の原則）から
導かれている。手順が実態と合わなくなったら、原則に立ち返って手順を組み直し、
本書を更新する。本書に書かれたコマンドは実行して検証できる——動かなく
なっていれば、それ自体が本書の古さの検出である。

## 0. 前提となる配置

```
aozora/
├── aozora2/          # 本体（このリポジトリ）
├── aozora2html/      # 参照実装（Ruby）。挙動の実測に使う
├── aozorabunko/      # コーパス（cards/ 以下に作品）
└── aozora-htmlcheck/ # 適合性ハーネス・オラクルアーカイブ（oracle/）
```

## 1. 全作業共通の不変条件

どの種類の作業でも、コミット前に以下をすべて満たす。

1. 全テストが通る:
   ```
   cd aozora2 && cargo test
   cargo test -p aozora-core --all-features   # 交換形式の適合フィクスチャ・不変条件
   ruby tools/verify_ast_spec.rb              # 交換形式の仕様と実出力の照合
   ```
   **重要**: 交換形式（`data/conformance/*.json`）の適合テストは `serde` フィーチャ配下に
   あるので、素の `cargo test` では **0 件で素通りする**。必ず 2 行目も走らせること。
   `tests/invariants.rs` は 2 つの AST が仕様で謳う不変条件（RawAST の可逆性、
   Aozora AST の解決済み・マーカーレス等）を検査する。適合フィクスチャは
   スナップショット比較なので、不変条件はそちらが受け持つ。
   `tests/interchange.rs` は 2 つの交換形式の往復（テキスト → JSON → HTML が
   テキスト → HTML と一致すること、RawAST が原文に戻ること）を縛る。
   ワークスペース全体の `--all-features` は GUI（GTK）の依存を引くので使わない。
   フィクスチャは実装から再生成する（差分を目視してからコミットする）:
   ```
   UPDATE_CONFORMANCE=1 cargo test -p aozora-core --features serde --test conformance
   ```
2. 適合性の回帰がない（悪化 0）:
   ```
   cd aozora-htmlcheck && cargo build --release
   ./target/release/aozora-htmlcheck --oracle-dir oracle \
       --baseline baseline-oracle.jsonl --out results-oracle.jsonl
   ```
   **重要**: ハーネスは aozora2 を `aozora2::html::convert` としてライブラリ
   リンクする。aozora2 側だけ `cargo build` してもハーネスのバイナリには
   反映されない。必ず `aozora-htmlcheck` ディレクトリで `cargo build --release`
   を実行してから走らせること（さもないと旧コードで比較し、悪化0 が偽になる）。
   改善が出たら baseline を更新し、同じコミットに含める:
   ```
   ./target/release/aozora-htmlcheck --oracle-dir oracle \
       --baseline-out baseline-oracle.jsonl --out results-oracle.jsonl
   ```
3. 挙動を意図的に変える場合、その変更は次のどちらかである:
   - 互換性の改善（オラクルへの接近）
   - Quirk フラグ配下の切り替え可能な挙動
4. コミットメッセージに「何を・なぜ・参照実装/注記一覧のどこに対応するか」を
   過去形で書く。コミット履歴は腐らない一次記録である。
5. コメントに規範を書かない。規範はテストへ。コメントは参照ポインタまで。

## 2. ループA: 互換性修正（オラクルとの差を埋める）

2025-26 の互換性改修（byte 一致 78%→98%）で実証された手順。

1. **観測**: ハーネスを回し、残差を種類別にクラスタリングする
   （results-oracle.jsonl の diffs を kind × path で集計し、件数と代表例を出す）。
2. **診断**: 代表例の最初の相違箇所とソース行を突き合わせる:
   ```
   cd aozora-htmlcheck && ./diagnose.sh <対象zip>
   ```
3. **実測**: 参照実装に最小入力を与え、期待挙動を確定する。**推測で実装しない**:
   ```
   cd aozora2html && ruby -Ilib bin/aozora2html 入力.txt 出力.html
   ```
   最小入力は CP932・CRLF で作る。例:
   ```
   python3 -c "open('t.txt','wb').write('題\n著\n\n本文\n\n底本：「甲」乙\n'.replace('\n','\r\n').encode('cp932'))"
   ```
4. **固定**: 期待挙動をテストに書く（名前だけで規則が分かるように）。
5. **修正**: 実装を直す。
6. **計測**: 不変条件 1・2 を確認する。「改善 N・悪化 0」以外の結果になったら、
   原因を潰すか revert する。悪化を抱えたまま先へ進まない。
7. **記録**: コミットする（不変条件 4）。

進め方のコツ:

- 一度に 1 規則。悪化 0 を絶対に崩さない。
- 効果（何件直るか）で優先順位を付ける。差分クラスタの件数がそのまま見積りになる。
- 参照実装の Ruby コードを読むときは、対応する実測を必ず添える
  （コードの読み違いは実測で発覚する）。

## 3. ループB: 参照実装のバグ・実装都合に遭遇したら（Quirk 化）

**判定基準**——いずれかに該当すれば Quirk:

- 規格上不正な HTML を生む（例: 属性値の中にタグが入る）
- 無意味な出力（例: 空の `width="" height=""`）
- 記法の使い分けとして作者が意図しえない差
  （例: bare「字下げ終わり」と「ここで字下げ終わり」の `<br/>` 差）

該当しない出力差（レイアウトの流儀・改行数の設計など）は通常の互換実装として
ループAで扱う。

手順:

1. `Quirks` にフラグを追加する（既定オン＝参照実装一致）。
2. on / off 両方の挙動をテストで固定する（ペアテスト必須）。
3. architecture.md 5 章の決定記録に日付つきで追記する。

## 4. ループC: 挙動不変リファクタリング

1. 大規模な場合は事前に全件出力スナップショットを取る:
   ```
   cd aozora-htmlcheck && python3 snapshot.py /tmp/snap_before.txt
   ```
   完了後に再取得して byte 一致を確認する。
2. 小さく刻み、各段で不変条件を確認してコミットする。
3. 方向は architecture.md 2 章・4 章へ向かうものに限る:
   型の壁を強める / 規範をテストへ移す / 文字列詮索を減らす / 1 規則 1 箇所へ寄せる。
4. 迷ったら revert。リファクタリングは機能を増やさないので、
   失敗を抱え込む価値がない。

## 5. ループD: 三者照合（注記一覧・コーパス・実装のドリフト対応）

三者は完全に一致せず、それぞれ更新されながら共進化する。照合は恒常作業である。

**未対応記法の検出**: 未実装・未解決の記法は、出力に
`<span class="notes">［＃…］</span>`（注記としての素通し）として必ず表面化する。
生成 HTML からこれを集計すれば、未対応記法の一覧と頻度が得られる。
件数上位から、注記一覧・コーパス実例・参照実装の挙動を照合して対応を決める。

**コーパスが更新されたら**: 新規・改版作品をハーネスの対象に加える
（`build_oracle.sh` は生成済みをスキップするので増分で回る）。
処理不能・未対応記法・回帰が出れば上記とループAで処理する。

**注記一覧が更新されたら**: 差分を読み、実装挙動・コーパス実態と照合する。

- 参照実装が既に対応している記法 → 実測（ループA手順 3）で期待挙動を確定する。
- どの実装も未対応の新記法 → 注記一覧の記述とコーパス実例から期待挙動を決め、
  根拠を決定記録に残し、テスト → 実装の順で作る。

**矛盾したら**: 既定則は architecture.md 3 章
（互換モードの挙動は参照実装が勝つ / バグは Quirk へ / 公開 HTML は権威にしない）。
既定則から外れる判断をしたときは必ず決定記録に残す。

## 6. 知識の置き場所

| 知識 | 置き場所 |
|---|---|
| 挙動の規則 | テスト（規則が読み取れる名前を付ける） |
| なぜそうしたか | コミットメッセージ（過去形）・architecture.md 5 章の決定記録 |
| 設計方針の変更 | architecture.md の本文改訂＋決定記録への追記 |
| 作業手順の変更 | 本書の改訂 |
| コメント | 参照ポインタのみ。規範を書かない |

テストの書き方:

- 名前だけで規則が分かるようにする
  （例: `test_kokode_close_suppresses_break_but_bare_does_not`）。
- 期待値は参照実装の実測から取る（ループA手順 3）。
- Quirk はペアテスト必須（ループB手順 2）。

### 命名・同居の規約（記法語を正準トークンにする）

architecture.md 2.1 性質5「ある記法の定義・意味・実例が grep 一発で揃う」を
満たすための規約。**結合キーは記法語そのもの**——`［＃…］` に現れる日本語
（`傍点`・`中見出し`・`返り点` など）を正準トークンとする。理由: 記法語は
コーパス・注記一覧・参照実装・本実装のすべてに共通して現れる唯一の語彙であり、
英名（`SesameDot` 等）は内部都合で揺れる。

規約:

- 記法の**定義**（パース分岐・記法語→型のマッピング）は記法語の文字列を
  リテラルで含む。
- 記法の**実例**（テスト）は入力文字列に記法語をそのまま書く。テスト名は
  英名でよいが、本文に記法語が無いと grep から漏れる。
- 将来のデータ表の**行**も記法語をキーに持つ（データ駆動化の前提）。

現状: `grep 傍点` で定義・レンダリング・テスト保有ファイルが揃う（記法語は
テスト本文の入力に必ず現れるため）。この性質はテスト名の英名化では壊れないが、
入力を変数へ追い出す・記法語を定数に逃がす等をすると壊れる。壊さないこと。

同じ対応表を二箇所に書く場合（例: `StyleType::from_command` と
`command_name`）は往復ガードのテストで縛り、片方だけの改修を検出可能にする
（誘因整合）。最終的にはデータ駆動化で一表へ畳む。

## 7. 検証インフラの維持

- インフラ（ハーネス・オラクル・baseline）が壊れたら、他の作業より先に直す。
  守衛が死んだ状態で作業しない。
- オラクルを再生成・追加したときは、来歴（生成日・参照実装のリビジョン）を
  `oracle/` に添える。
- baseline の更新は「改善をコミットするとき」に行う（不変条件 2）。

着手する契機は「具体的な正しさの欠陥（現状の詮索では再現できない参照挙動）が
出たとき」。そのときは `classify_output_line` / `LineInfo` を継ぎ目として、
該当行種だけをノード由来判定へ差し替える（全面書き換えではなく局所置換）。

**残差クラスタリングとループA（2026-07 実施）**: different 328件を「最初の
相違の前後を数値・非ASCIIを正規化した署名」でバケット化して観測した
（手順は下記「残差観測」）。最大クラスタ群は burasage（折り返し字下げ）行の
包み方の差で、複数バケットに分散して合計で最多。次点にヘッダのエスケープ差、
末尾 `<br/>` 数、gaiji 一覧、gaiji alt 書式など。

**指標の注意（重要）**: ハーネスの「改善/悪化」カウンタは構造的同等
（structural equivalence）粒度で、byte 非一致でも構造同等なら悪化に数えない。
**真の互換指標は byte-exact 件数**（results の status=="exact" の数）。
リファクタの挙動不変確認や改善計測は、改善/悪化カウンタだけでなく
byte-exact 件数の増減で判断すること。error（status!=exact/different/equivalent）は
オラクル gz が無い作品で、byte-exact の実効上限は 17509−error になる。

**error の正体（2026-07 調査で確定。旧記述「CRC 不良 zip」は誤り）**: オラクル
build（build_oracle.sh）は参照実装 aozora2html が**終了コード0で完走したときだけ**
gz を作る。error はハーネスが選んだ zip エディションで**参照実装自身が失敗**して

**`UnclosedAccentBreak` を Quirk にしない判断（2026-07-31）**: これは青空文庫の記法ではない。
「ここで改行」に当たる書き方は無く、これを生むのは未閉じ `〔` ——**入力側の誤り**だけなので、
変種の名前は効果（素の `<br />`）ではなく原因にしてある。誤りであること自体は
`ParseDiagnosticKind::UnclosedAccent` が別に伝える。

Quirk にはしない。判定基準の「作者が意図しえない差」には当たる（マージ単位の後半が空だと
閉じタグの前に `<br />` が 2 つ並ぶ）が、**オフ側の正しい出力が AST から決まらない**。
後半が `［＃ここから…］` のマージは `<br />` が 1 本でよく、後半が空行のマージは 2 本とも
要るのに、どちらも `Line` の形は同じ（`[…, UnclosedAccentBreak]` ＋ `brk: Br`）で区別が
つかない。区別するには「後半の行種」を運ぶ互換メタデータが要り、それは今回 `RawLine` から
外したものそのもの。実測でも影響は小さい——コーパス全件で `UnclosedAccentBreak` は
52 箇所 / 29 作品、うち行末（余分な `<br />` が出うる位置）は 9 箇所 / 6 作品。

**リスクが小さいことの実測**: コーパス全件を走査したところ、「折り返し開始行に同行本文が
ある」のは 248 作品に見えたが、**247 件は注記凡例（`-----` で囲まれたヘッダ）の中**の
見本行（`（例）［＃ここから改行天付き、折り返して１字下げ］`）で本文として描画されない。
本文に限ると該当は **1 行 1 作品**（58012）だけ。未閉じ `〔` を含む本文行は 53 行 29 作品。
旧メモの「触ると大規模悪化」は BlockManager の close ロジックに由来する警戒で、この
行マージ自体の影響半径ではなかった。

- **burasage 入れ子の閉じ**: 43672 は jisage 内の burasage 閉じだが、参照の div が
  **32/31 で不均衡**（我々は 32/32）。下の「div タグ均衡差」と同じ理由で追随しない。
- **外字が絡む注記で参照が説明を落とす（参照バグ）**: 2665/49891/49905/58400/58401。
  `［＃「すはどり」に「※［＃「尸＋鳥」、第4水準2-94-2］鳩」の注記］` のように注記へ外字が
  入ると、参照は前方参照の対象も注記本体も捨てて `alt="※()"` の画像だけを出す。機序は
  2 つ重なっている。(1) `exec_style` は最初に `kuten2png(spec)` を試し、戻り値が変われば
  即採用して `targets` を捨てる。`kuten2png` は面区点を文字列のどこからでも拾うので、
  入れ子コマンドが**先に解決された結果の `<img src=".../2-94-02.png">`** を利用者が書いた
  句点コード指定と読み違える（`※.*※` ガードも元テキスト前提なので素通り）。
  (2) `EmbedGaiji.new(…, desc.gsub!(IGETA_MARK, ''), …)` の `gsub!` は置換が無いと `nil` を
  返すため alt が `※()` になる。`非0213外字` を混ぜて (1) のガードに掛けるだけで正しい
  入れ子ルビが出ることを実測済み。こちらは正しい HTML を出しており、追随には per-case な
  Quirk が要る。
- **62685（参照バグ）**: `“［＃縦中横］i《アイ》［＃縦中横終わり］”` で参照が
  `<ruby><rb><span dir="ltr">i</rb>…</ruby></span>` と**タグを交差**させる（不正 HTML）。

**「参照バグ」と誤分類していた 4 件（実は当方の不具合・2026-07-31 修正済み）**:
- **789/49940**: アクセント `〔…〕` の走査が入れ子の注記 `［＃…］`・外字 `※［…］`・
  ルビ `《…》` を飛ばしていなかった。参照 `AccentParser#parse` は 1 文字ずつ読んで

- **49946**: ブロック形 `［＃ここから窓中見出し］` で 窓/同行 スタイルを拾い忘れ
  （行内形だけ拾っていた）。あわせて見出しブロックの閉じが `CloseKind::NoBreak` を
  無視して常に改行していたのを修正（`［＃ここで…終わり］あと` が同じ行に続く）。
