# aozora2 アーキテクチャ設計メモ

改訂: 2026-07

青空文庫記法テキストを HTML（将来的には EPUB・プレーンテキスト等）へ変換するツール
aozora2 の設計方針をまとめる。

## 0. この文書の位置づけ（最初に読むこと）

**この文書は規範ではなく、失われてもよい案内図である。** 実態（ビルドが通り、
テストが通るコード）と食い違ったら、この文書が古い。本文で定義するのは
「この文書が失われても困らない構造」であり、文書自身はその構造の一部ではない。

- 目標: 青空文庫の記法とデータを 100 年以上保守する。担い手は何度も入れ替わり、
  設計文書は失われ・読まれず、コメントは腐り、当初設計から外れたコードが混入する
  前提で、**知らない誰かが新しく正しいプロセッサを書け、記法とコーパスを拡張し
  続けられる**体制の基盤をつくる。
- 前提の機能要件: 参照実装 [aozora2html](https://github.com/aozorahack/aozora2html)
  と機能的に等価（互換モードでは byte 一致）であること。
- 工数・ツール自体の後方互換性は評価軸に含めない。最終成果物の良さのみを基準とする。

## 1. 一次資料と真実のモデル

### 1.1 一次資料は二つ

1. **コーパス**（青空文庫のコンテンツそのもの）
2. **ソースコード**（記法定義データ・型・テストを含む。実行系が消費するデータは
   コードの一部である）

これ以外のあらゆる文書（本メモ・生成された仕様書・コメント）は派生物であり、
権威を持たない。

### 1.2 荷重原則

> 真実は「偽になったとき何かが壊れる場所」にだけ置く。

- コードは実行されるので、自分の挙動について嘘をつけない。
- 実行されるテスト・doctest は、偽になると CI が赤くなる。
- パーサが消費する定義データは、壊れるとパースが壊れる。
- コミットメッセージ・日付つき決定記録は過去形の事実であり、腐らない。
- 現在形の prose（コメント・文書）は、嘘になっても何も壊れない。**規範を書かない。**

### 1.3 誘因整合の原則

> 守衛（CI・検査）は、それを外すことが外した本人の損になるときだけ生き残る。

強制ゲートもまた可処分物である。ドキュメント更新を強要する CI は、将来の担い手に
とって摩擦でしかなく、仕様が更新される代わりに**ゲートが削除されて終わる**。
したがって:

- 担い手自身が欲しがる検査だけを置く（「この変更は 17,000 作品の出力を壊す」と
  教える適合性テストは、担い手自身の利益なので生き残る）。
- 文書の更新・整備を強制する仕組みは置かない。文書は生成物にする（2 章）。
- 網羅性の不足はゲートで防ぐのではなく**可視化**する（生成された仕様に
  「実例なし」と表示される穴は、消しても得がなく、埋める動機だけを生む）。

### 1.4 置き場所の信頼度

| 置き場所 | 偽になったとき | 使い道 |
|---|---|---|
| コード（実行される） | 挙動そのもの | 一次資料。挙動の定義 |
| 実行されるテスト・doctest | CI が赤くなる | 規則の固定・実例 |
| パーサが消費する定義データ | パースが壊れる | 言語の定義 |
| 型・crate 依存グラフ | コンパイルが落ちる | アーキテクチャ（層の壁） |
| コミット履歴・日付つき決定記録 | 腐らない（過去形） | 「なぜ」の記録 |
| 生成された仕様書 | 古いレンダーになるだけ | 読み物。権威なし。いつでも再生成 |
| 手書き prose・コメント | 何も壊れない | 規範禁止。ポインタと薄い案内のみ |

## 2. 仕様の扱い: 「書く」のではなく「起こせる」ようにする

手で書かれ・実行されず・コードと乖離しうる仕様書には頼らない。
代わりに、**コードから仕様書を起こすことが容易であること**を
コードのアーキテクチャ要求として課す。

### 2.1 コードに要求する構造的性質

1. **記法定義はパーサが消費するデータ**（安定 ID つき）。
   青空文庫「注記一覧」に対応する規則索引で、実行系がこれを解釈して動く。
   消費されるので実装と乖離できない（荷重原則）。
   コードの脇に置かれるだけの参照用テーブルは構造化されたコメントに過ぎず、
   同じ速度で腐るため不可。
2. **1 規則 ↔ 1 箇所**。テーブル項目・意味の型・その規則を固定するテストが、
   規則 ID で紐付いて同居する。人（または生成器）がコードを歩けば、
   言語の全 surface を機械的に列挙できる。
3. **実例は実行されるテストとして規則の傍に置く**。Rust の doctest は
   「偽になると壊れる文書」であり、この用途の標準装備。実行されない
   コードブロックを文書に書かない。
4. **Quirks は列挙可能な型＋ on/off ペアテスト**。互換プロファイル
   （参照実装のバグ・実装都合の全列挙）が機械可読になる。
5. **仕様生成器**（目標: `aozora2 spec`）。規則テーブル・テスト実例・Quirks を
   歩いて仕様書（人間可読＋機械可読）を出力する。バイナリ自身が自分の言語定義を
   印字できる＝コードだけを持つ将来の読者が、追加インフラゼロで仕様を得られる。

### 2.2 生成された仕様書の性質

- 手で書かない・編集しない。権威を持たない。生成日付つきスナップショット。
- 失われてよい（いつでも再生成できる）。
- 乖離は「古いレンダー」にしかならず、一次資料を汚染しない。
- 実例の無い規則は「実例なし」と表示される（穴の可視化。ゲートではない）。

### 2.3 復元可能性

仕様書どころか上記の構造が未整備でも、次の 5 点が揃っていれば挙動の仕様は
再導出できる: (1) コーパス (2) オラクルアーカイブ (3) 適合ケース
(4) 動く実装 (5) 差分ハーネス。2025-26 の互換性改修は、設計文書ゼロの状態から
参照実装とコーパスの考古学だけで約 30 規則を再発掘した**復元ループの存在証明**
である。

ただし**意図（なぜ）だけは挙動から復元できない**。実例: bare「字下げ終わり」と
「ここで字下げ終わり」の `<br/>` 差は、挙動は復元できたが、意図は
「使い分けの意図は無い（実装都合）」と推定するしかなかった。よって決定時に
コミットメッセージ・決定記録（5 章）へ過去形で残すことだけが保険になる。

## 3. CI: 一次資料の守衛

CI はコーパスとコードを守る従者であり、権威ではない。置くのは担い手自身が
欲しがる検査のみ（誘因整合）:

- **適合性**: オラクルアーカイブ（参照実装 aozora2html の全 17,397 件の出力、
  aozora-htmlcheck リポジトリの `oracle/`）との構造比較・byte 比較。
  `--baseline` で回帰を即検出。アーカイブはデータなので、参照実装（Ruby）が
  実行不能になっても互換性の定義は残る。
- **コーパス全件が処理可能であること**。
- **Quirk ペアテスト**: 各 quirk は on/off 両方の挙動をテストで固定する。
- （将来）プロパティベーステスト: ランダムな正当記法で実装間の一致を検証。

### 真実源の優先順位

真実源は三つあり、互いに矛盾する。矛盾時の解決ポリシー:

| 真実源 | 位置づけ | 矛盾したら |
|---|---|---|
| 注記一覧（青空文庫の公式ドキュメント） | 意図 | 意味論の第一参照。ただし挙動の最終判定には使わない |
| 参照実装 aozora2html | 事実上の挙動 | **互換モードの挙動はこれが勝つ**。ただしバグ・実装都合は Quirks として隔離しラベル付けする |
| 公開コーパス（cards/ の HTML） | 現実 | 権威としない（約 6 割は古い世代の生成器の出力のまま） |

## 4. コードのアーキテクチャ（一つの適合実装として）

```
ソース
  → [記法定義データ] を解釈するパーサ
  → RawAST（忠実・前方参照未解決・ブロックは平坦マーカー。位置つきが望ましい）
  → Lowerer（前方参照解決・ブロック部分木化・行束ね・break 計算）
  → 中立AST（block / line / inline の木）
  → 各バックエンド（HTML / EPUB / plain text …）
  ＋ Quirks（参照実装の癖を隔離・明示ラベル）
```

### 4.1 中立AST（block / line / inline）

青空文庫記法の論理構造は **ブロック ⊃ 行 ⊃ インライン** の 3 層。

```rust
// 概念図
enum Block {
    Line { inline: Vec<Inline>, brk: Break },          // 内容の1行
    Nested { kind: BlockKind, children: Vec<Block> },  // 字下げ/地付き/見出し/ぶら下げ…
}
enum Inline { Text, Ruby { base, ruby }, Style, Gaiji, Accent, Img, Tcy, /* … */ Note }
```

- **行は第一級の構造ノード**（行スコープのコマンドが存在し、ソース 1 行 ≒
  作品の論理行であるため、行は構造である）。
- **ブロックは部分木**。「ブロックだけの行」は器（Nested）に吸収され、
  `<br/>` 特別扱いの多くが構造から自然に従う。
- **インライン葉は raw/ast で共有**。未確定/マーカー系（親文字未確定の
  `PendingRuby`, `UnresolvedRef`, ブロックマーカー, `LineJisage`）だけ raw 専用。
- Rust らしい自然な型（enum + `Vec`）に収め、型トリックは入れない。

### 4.2 型の壁（ドリフト対策の中核）

「設計から外れたコードが**書けない**」ことをコンパイラに強制させる。
コメントや規約による抑止はドリフトに敗ける前提。

- 中立AST の型に Raw 概念を含めない → レンダラに死にアームが存在し得ない。
- バックエンドには中立AST だけを渡し、ソース文字列を渡さない
  → 生の行を再パースするハックが書けない。
- crate 分割で依存方向を固定（Rust の crate グラフは非循環なので層違反は
  ビルドエラー）。将来: 記法定義データ＋型 / core / 各バックエンド。

### 4.3 Quirks

byte 互換のためだけに再現する「参照実装のバグ・実装都合」を、意味と分けて
`Quirks` フラグに隔離する（実装済み）。既定オン＝参照実装一致、
`Quirks::none()` で規格準拠出力。terprip の `<br/>` 残余
（bare/ここで差）も意味ではなく実装都合であり、`Line.brk` の互換メタデータ
として 1 本のチャネルに封じ込める。

### 4.4 位置情報（任意・品質向上）

ノードにソース位置を持たせると精密な診断・リンタの土台になり、コーパス拡張
（新規作品の検証）を支える。lossless CST は品質向上要素であり、
生存性には直交。優先度は上記の構造的性質より下。

## 5. 決定記録（日付つき・追記のみ）

過去形の事実として記録する。腐らない。

- **2026-07** 公開 HTML をオラクルにしない。実測で公開 HTML の約 6 割が古い世代の
  生成器の出力のまま（400 件標本で現行参照実装と byte 一致 41%）であり、
  参照実装の出力を全件生成してオラクルとした。
- **2026-07** 参照実装のバグは再現しつつ Quirks に隔離する。互換（既定オン）と
  規範（`none()`）を単一実装で両立し、将来フラグごと落とせる形にする。
- **2026-07** 行を第一級の構造ノードとする。行スコープコマンドの存在と
  「ソース 1 行 ≒ 論理行」から、行は構造であると判断。
- **2026-07** terprip の `<br/>` 差（bare/ここで）は意味ではなく実装都合と判断し、
  互換メタデータ（`Line.brk`）として隔離する。
- **2026-07** 木化より記法のデータ駆動化が先。最深の負債は記法の定義がコードの
  副作用としてしか存在しないこと。
- **2026-07** コードを挙動の一次資料とする。意図の担体としては信頼せず、
  型の壁で強制する。コメントに規範を書かない。
- **2026-07** **仕様書に権威を置かない。** 手書きの仕様書は腐敗・乖離し、
  更新を強制するゲートは削除されるだけ（誘因整合の原則）。一次資料はコーパスと
  ソースコード、CI はその守衛、仕様書はコードから生成する派生ビューとする。
  「コードから仕様書を起こすことが容易」をアーキテクチャ要求として課す
  （2 章の構造的性質 1〜5）。docs/spec/ への prose 書き起こし計画は取り下げ、
  コメントの規範内容をテストへ移す監査に置き換えた。

## 6. 移行の段階（実施状況）

byte 一致を安全網に、挙動不変を保ちながら刻む。

- **段1（完了）**: パーサと Lowerer の継ぎ目を型で導入（`RawAst`/`Ast`、
  `parse_raw` → `lower`）。挙動不変。
- **段2a（完了）**: 文書単位の RawAST を実体化（`RawLine`/`RawDoc`）。
  「文書単位パース → 行ごと描画」に分離。挙動不変。
- **コメント→テスト監査（次の優先）**: 2025-26 の互換性改修で発掘した規則は
  大部分がテスト（約 50 本）とコミット履歴に載っており耐久層にある。
  残る腐敗リスクは規範を運ぶ長文コメント。内容をテストで固定されているか監査し、
  不足分をテスト化、コメントは参照ポインタへ薄める。
- **規則 ID の導入**: 規則・テスト・（将来の）テーブル項目を紐付ける安定 ID。
- **記法のデータ駆動化**: 注記一覧に対応する規則テーブルを、パーサが消費する
  荷重形で導入（2 章の性質 1・2）。
- **仕様生成器 `aozora2 spec`**（2 章の性質 5）。
- **段2b/2c**: Lowerer によるブロック部分木化・`Line.brk` 集約、
  BlockManager と文字列詮索の撤去（4 章の型の壁の完成）。
- **（将来）位置情報・プロパティベーステスト**。

## 8. 用語

| 用語 | 意味 |
|---|---|
| 一次資料 | コーパスとソースコード。権威を持つ唯一の層 |
| 荷重原則 | 真実は「偽になったとき何かが壊れる場所」にだけ置く |
| 誘因整合の原則 | 守衛は、外すことが外した本人の損になるときだけ生き残る |
| RawAST | パーサが記法を忠実に変換した木（前方参照未解決・ブロックは平坦マーカー） |
| Lowerer | RawAST → 中立AST への変換処理 |
| 中立AST | バックエンドが消費するクリーンな木（block / line / inline） |
| Quirks | 参照実装のバグ・実装都合を byte 互換のためだけに再現する挙動の隔離フラグ群 |
| オラクル | 参照実装 aozora2html の全件出力アーカイブ（互換性の判定基準・データ） |
| 注記一覧 | 青空文庫が定める記法の公式ドキュメント。記法定義データの源 |
| 規則 ID | 記法・挙動の規則ごとの安定識別子。テスト・テーブル・生成仕様を紐付ける |
| 仕様生成器 | コード（テーブル・テスト・Quirks）から仕様書を出力する道具。`aozora2 spec` |
