# aozora2 アーキテクチャ設計メモ

青空文庫記法テキストを HTML（将来的には EPUB・プレーンテキスト等）へ変換するツール
aozora2 の、目標とする設計方針をまとめる。100 年以上続くプロジェクトを前提に、
**「参照実装の移植物」から「記法仕様の実装」へ**質を変えることを狙う。

- 対象読者: 現在の設計を知らずにコードを引き継ぐ将来のメンテナ
- 前提の唯一の機能要件: 参照実装 [aozora2html](https://github.com/aozorahack/aozora2html) と
  **機能的に等価**（互換モードでは byte 一致）であること
- 工数・ツール自体の後方互換性は評価軸に含めない。**最終成果物の良さのみ**を基準とする

---

## 1. 現状（2024 時点）と最深の負債

### 1.1 現在のパイプライン

```
ソーステキスト
  → tokenizer（1文字ずつ走査して Token 列: Text / Ruby / Command / Gaiji / Accent）
  → parser（Token → Node。［＃…］注記を文字列マッチで解釈。前方参照は未解決）
  → resolver（前方参照の解決: ルビ親文字・「対象」に傍点 等）
  → renderer（HTML 生成。ブロックの入れ子を BlockManager スタックで管理）
```

段階的リファクタで以下は導入済み（詳細は本文書 4 章）:

- `RawAst` / `Ast` の root 型と `parse_raw` → `lower` の継ぎ目（段1）
- 文書単位の `RawDoc` 実体化（段2a）
- 前方参照 spec の型付き化（`RefSpec`）、CSS クラスの AST からの追い出し 等

### 1.2 最深の負債: 「言語」が形式的に定義されていない

現状も、これまでの改修も、**青空文庫記法という言語の定義が「参照実装を移植したコードに暗黙的に埋まっている」だけ**である。

- `［＃…］` 注記（数十種の小言語）は、`command_parser` / `block_parser` /
  `reference_parser` に散在する手続き的な文字列マッチ（`contains("字下げ")`,
  `starts_with("ここから")` 等）で解釈されている。
- 記法の全 surface が一箇所で見渡せず、公式ドキュメント
  （青空文庫「注記一覧」）と実装が乖離しうる。

10 年後の引き継ぎで最も必要なのは「この記法は何か」の権威ある定義だが、
それが**コードの副作用としてしか存在しない**。これが根治すべき最深の負債である。

## 2. 目標アーキテクチャ

設計の重心を「参照実装の移植」から「記法仕様の記述」へ移す。

```
ソース
  → [注記一覧＝データ駆動の記法定義] を解釈するパーサ
  → 位置つき構文木（理想は lossless CST）
  → Lowerer（前方参照解決・ブロック部分木化・行束ね・break 計算）
  → 中立AST（block / line / inline の木）
  → 各バックエンド（HTML / EPUB / plain text …）
  ＋ Quirks（参照実装の癖を隔離・明示ラベル）
  ＋ 適合性テスト（オラクル ＋ プロパティベース）
```

各層を以下で詳述する。

### 2.1 記法をデータ駆動で宣言する（この領域の肝・最大の長期価値）

`［＃…］` 注記を手続き的マッチで散らすのをやめ、**宣言的なテーブル**にする。
青空文庫「注記一覧」に一対一で対応させる。

```rust
// 概念図（Rust の具体形は要検討）
struct NotationRule {
    /// 記法のパターン（"N字下げ", "地から N 字上げ", "「対象」に 傍点" など）
    pattern: NotationPattern,
    /// 対応する意味（ノード種別）
    kind: NotationKind,
}

enum NotationKind {
    BlockIndent(u32),            // ［＃N字下げ］
    RaiseFromBottom(u32),        // ［＃地からN字上げ］
    ForwardRef(RefSpec),         // ［＃「対象」に傍点］
    // …注記一覧の全項目
}
```

効果:

- 記法の追加・変更が**データ編集**になり、コード改修でなくなる
  （100 年スパンで記法は増える前提）。
- 記法の全 surface が**一箇所で見渡せる**＝ドキュメントと実装が一致。
- パーサはこのテーブルを解釈する薄い機構になる。

これは「木化を頑張る」よりも、実際に一番厄介な**アドホックな注記解析を根治**する。
一つだけ着手するならここが最優先。

### 2.2 位置つき構文木（できれば lossless CST）

最終品質を最優先するなら、**各ノードがソース位置（byte 範囲）を持つ**構文木にする。

- 中間案（推奨の下限）: 「位置つき AST」。ノードに source span を持たせるだけで、
  精密なエラー報告（「N 行目のこの注記が閉じていない」）・ソースマッピング・
  将来のエディタ / リンタ / 整形ツールの土台になる。
- 理想形: **rowan 型の lossless CST**（rust-analyzer 方式）。全 byte を保持し、
  往復可能・増分再解析・エラー回復を備える。純粋な変換器には過剰だが、
  「100 年・ツール群が育つ」前提なら理論的な最上位。

純粋な text→HTML 変換だけなら位置なし AST でも足りる。ツール化を見込むかで選ぶ。

### 2.3 中立AST（block / line / inline の木）

レンダラが消費するクリーンな木。バックエンド非依存で、HTML/CSS の詳細を持たない。

青空文庫記法の論理構造は **ブロック ⊃ 行 ⊃ インライン** の 3 層で、
Markdown/HTML の block/inline 分割と同型。

```rust
// 中立AST（概念図）
enum Block {
    Line { inline: Vec<Inline>, brk: Break },          // 内容の1行
    Nested { kind: BlockKind, children: Vec<Block> },  // 字下げ/地付き/見出し/ぶら下げ…
}
enum Inline { Text, Ruby { base, ruby }, Style, Gaiji, Accent, Img, Tcy, /* … */ Note }
```

設計上の要点:

- **行は第一級の構造ノード**。青空文庫記法で行はレンダリングの都合ではなく
  構造である（行スコープのコマンド `［＃地付き］`・一行 `［＃N字下げ］` が存在し、
  ソース 1 行 ≒ 作品の論理行）。
- **ブロックは部分木**。`BlockStart`/`BlockEnd` の平坦マーカーではなく
  `Nested{kind, children}`。これにより「ブロックだけの行」は器（Nested）に
  吸収され、`<br/>` 特別扱いの多くが構造から自然に従う。
- **インライン葉は raw/ast で共有**。raw と ast で本当に違うのは構造層だけで、
  インライン内容（Ruby/Text/Gaiji…）は同一。全葉を二重定義しない。
- **未確定/マーカー系だけ raw 専用**（`PendingRuby`（親文字未確定のルビ）,
  `UnresolvedRef`, ブロックマーカー, `Close{explicit}`, `LineJisage`）にして、
  中立AST から不正状態・マーカーを型で締め出す（レンダラの防御的な死にアームが消える）。
- root 型で raw / ast を判別できれば十分。全ノードを機械的に二重定義する
  トリッキーな作りにはしない。Rust らしい自然な型（enum + `Vec`、`Box` は必要な所だけ）
  に収め、GAT 等の型トリックは入れない。

### 2.4 多バックエンド

中立AST を HTML/EPUB/plain text/将来形式が共有する。バックエンドは中立AST の
**木歩き**に徹し、状態機械も文字列詮索も持たない。

### 2.5 Quirks: 参照実装の癖を隔離・明示ラベル

byte 互換のためだけに再現している「参照実装のバグ・実装都合」を、意味とは分けて
フラグに隔離する（実装済みの `Quirks` 機構を継続）。

- 既定オン（＝参照実装に一致）、`Quirks::none()` で規格に沿った出力。
- 各 quirk に「どの参照実装バグを再現しているか」を明記。将来まとめて落とせる。
- 例（実装済み）: 外字 alt 内の入れ子 `※［＃…］` の `<img>` 展開（不正 HTML）、
  画像の空 `width="" height=""`、アクセント名 `A^` の字母欠け。

**terprip の `<br/>` 残余**（bare `字下げ終わり` vs `ここで字下げ終わり` の
`</div>` / `</div><br/>` 差）も本質ではなく実装都合。中立AST は構造だけを持ち、
この差は `Line.brk` に**「aozora2html 互換・意味ではない」と明示ラベルした**
互換メタデータとして、Lowerer が計算して 1 本のチャネルに封じ込める
（文字列詮索をレンダラ全体に撒かない）。

### 2.6 適合性テスト

コード構造を参照実装に似せるのではなく、注記一覧に基づく論理モデルで書き、
byte 互換は**テストで固定**する。二本立て:

- **オラクル方式（実装済み・`aozora-htmlcheck`）**: 参照実装 aozora2html の出力を
  全 17,453 件生成してオラクルとし、aozora2 の出力と HTML Living Standard の
  パースアルゴリズムで構造比較 ＋ byte 比較。`--baseline` で回帰を即検出。
  （公開 HTML は 4 割しか現行参照実装を再現しないため、公開 HTML ではなく
  参照実装の出力をオラクルにしている。）
- **プロパティベーステスト**: ランダムな正当記法を生成し、両実装の出力一致を検証。
  実コーパスだけでは網羅しきれない組み合わせの回帰を捕捉。

## 3. 設計判断の記録（なぜこの形か）

### 3.1 なぜ「木化を頑張る」より「記法のデータ駆動化」が先か

- 木化（中立AST）は良い中盤だが、**言語の定義を形式化しない**。最大の長期負債は
  「記法がコードの副作用としてしか存在しない」ことなので、そこを直すデータ駆動化が
  最も質を変える。
- 木化と記法データ駆動化は排他ではない。理想形は両方だが、価値の順は
  **データ駆動化 →（中盤の木）→ 位置つき/lossless・プロパティテスト**。

### 3.2 行が第一級構造である根拠

- 行スコープのコマンドが存在する（`［＃地付き］`・一行 `［＃N字下げ］`）。
- ソース 1 行 ≒ 作品の論理行（折り返し前の行）。物理行ではなく論理行。
- ブロックは行をまたいで含む（`［＃ここからN字下げ］…［＃ここで字下げ終わり］`）。

### 3.3 なぜ現行の平坦マーカー＋BlockManager を置き換えるか

現行はブロック構造がどこにも実体化されず、レンダラのループの一時状態としてのみ存在する。
「入力 → 構造」を検査・テストできない。木にすると構造が実体化され、
Lowerer 一箇所に厄介な規則（暗黙クローズ・道連れクローズ・ぶら下げ）が集約され、
レンダラは木歩きに単純化する。

※ ただし青空文庫は本質的に行指向・状態持ちの処理であり、木化は「厄介さを消す」
のではなく「一箇所に集約し明示する」ことに価値がある点に注意。木にするなら
**Block/Line/Inline の最小忠実モデル**に留め、投機的な一般化を入れないこと。

## 4. 移行の段階（実施状況）

byte 一致を安全網に、挙動不変を保ちながら小さく刻む方針。`aozora-htmlcheck` の
`--baseline` と、全件出力ハッシュの直接比較で各段の回帰 0 を確認する。

- **段1（完了）**: パーサと Lowerer の継ぎ目を型で導入。`RawAst`/`Ast` newtype、
  `parse_raw` → `lower`。挙動不変。
- **段2a（完了）**: 文書単位の RawAST を実体化。`RawLine`/`RawDoc`/`parse_document_raw`。
  パースと描画を「文書単位パース → 行ごと描画」に分離。挙動不変。
- **段2b（未着手）**: Lowerer がブロックを部分木に組み上げ、レンダラを木歩きに切替。
  BlockManager 撤去。現行の状態機械を忠実移植する大規模な書き直しで、byte 一致が
  唯一の安全網。
- **段2c（未着手）**: `Line.brk`（terprip 由来の改行）を Lowerer に集約し、
  レンダラの文字列詮索を撤去。
- **（将来）記法のデータ駆動化**: 注記一覧をデータ化し、パーサ front-end を刷新。
- **（将来）位置つき/lossless 構文木・プロパティベーステスト**。

なお、これまでのリファクタ（型付き `RefSpec`、`explicit_close` の第一級化、
CSS クラスの AST 追い出し、`RawDoc` 実体化）は、いずれも目標アーキテクチャの
「中盤（AST）」への前進であり無駄にならない。目標形が付け加えるのは主に
**前段（記法のデータ駆動定義）** と **横断要素（位置情報・プロパティテスト）**。

## 5. 用語

| 用語 | 意味 |
|---|---|
| RawAST | パーサが青空文庫記法を忠実に変換した木（前方参照は未解決、ブロックは平坦なマーカー） |
| Lowerer | RawAST → 中立AST への変換処理（前方参照解決・ブロック部分木化・行束ね・break 計算） |
| 中立AST | レンダラが消費するクリーンな木（block / line / inline） |
| Quirks | 参照実装のバグ・実装都合を byte 互換のためだけに再現する挙動を隔離するフラグ群 |
| オラクル | 参照実装 aozora2html の全件出力（byte 互換の判定基準） |
| 注記一覧 | 青空文庫が定める記法の公式ドキュメント。データ駆動の記法定義の源とする |
