# 外字注記辞書

青空文庫・外字注記辞書を機械可読にしたもの。`tools/extract_gaiji_chuki.rb` で
再生成できる。

外字注記そのものの記法と変換規則は [docs/spec-encoding.md](../../../docs/spec-encoding.md)
5 章。本書はその**外部データ**についての説明で、記法の仕様ではない。

- 出典: <https://www.aozora.gr.jp/gaiji_chuki/gaiji_chuki.pdf>
- 版: 青空文庫外字注記辞書編集グループ・**改訂第八版訂正版（2011-08-06）**
- 利用条件: 青空文庫本体と同じ

```
curl -O https://www.unicode.org/ivd/data/2022-09-13/IVD_Sequences.txt
curl -O https://raw.githubusercontent.com/cjkvi/cjkvi-ids/master/ids.txt
ruby tools/extract_gaiji_chuki.rb gaiji_chuki.pdf IVD_Sequences.txt ids.txt \
    crates/aozora-core/data
```

poppler-utils（pdftotext・pdftocairo）が要る。PDF 自体の読み取りは `tools/mini_pdf.rb`
（標準ライブラリのみ。この PDF は古典的な xref 表・FlateDecode のみ・オブジェクト
ストリーム無しなので、汎用の PDF ライブラリを持ち込まずに済む）。

`id` は `p<ページ>-<ページ内連番>` で、上の版のページ付けに依存する。版を上げるときは
2 つの TSV を同時に作り直すこと。

## `gaiji_chuki.tsv` — 9264 エントリ

| 列 | 内容 |
|---|---|
| `id` | エントリの識別子 |
| `page` | PDF のページ番号（字形を目で確かめたいときの参照先） |
| `radical` / `strokes` | 部首（202 種）と画数 |
| `desc` | 注記の説明**全文**（`※［＃「口＋畢」…］` の `口＋畢`） |
| `jis` / `level` | 面区点と水準（4041 件） |
| `unicode` | U+ の値（4068 件） |
| `sub` / `sub_kind` / `sub_rule` | 代用してよい字・種別・規準番号（1184 件） |
| `cross` | 別部首への再掲（★）なら 1 |
| `ivs` | 字形の Adobe-Japan1 異体字セレクタ列（799 件。例 `51E1 E0101`）。**1 パーツで描かれて
いる字だけ**。組み立ててある字は `gaiji_chuki_glyphs.tsv` 側で持つ |
| `cid` | 字形の CID（`ivs` が引けなかったときの手がかり） |
| `glyph` | `1` なら `gaiji_chuki_glyphs.tsv` に輪郭がある |
| `ids` | 説明を組み立ての IDS にしたもの（8338 件。例 `⿰旬力`） |
| `ids_char` | `ids` を CHISE の IDS 表で引いた字（6484 件） |
| `glyphwiki` | `ids` から作った GlyphWiki の合成グリフ名（例 `u2ff0-u65ec-u529b`） |

`ids` が 1 文字（984 件）のときは `ids_char` と `glyphwiki` を空にしてある。説明が字を
名指しているだけか、引き算や `〜のつくり` で 1 文字に落ちたかのどちらかで、後者は当てに
ならない（後述）。

**`jis` と `unicode` は排他**（両方が入る行は無い）。辞書が JIS X 0213 にある字を面区点
だけで書き、無い字を U+ で書くため。面区点から U+ が要るときは `data/jis2ucs.json` を引く
——4041 件すべて引ける。`unicode` 列は面区点の重複ではなく補集合なので、埋めてはいけない。

`desc` が**両方向の結合キー**になる。読む側は「説明だけの注記」を字へ解決でき、書く側
（OCR など）は字から慣用の注記を引ける。

そのため**説明は全文を持つ**。`※［＃「尅」の「寸」に代えて「土」］` の 「尅」 だけを採ると、
尅 そのものを指すエントリと同じ `desc` になって、結合キーとして使えない。外側の 「」 は
それが全体を包んでいるときだけ外すので、単純な注記は `口＋畢` のまま、外側にもう一段ある
1028 件だけが `「尅」の「寸」に代えて「土」` の形で残る。

これで**同じ `desc` で符号位置が食い違うのは 1 種**（`目＋來`）だけになった。それも辞書
自身の重複で、`※［＃「目＋來」］` を 7 画の 䀹 と 8 画の 睞 の両方に使っている。

`sub_kind` の内訳は包摂適用 1018・デザイン差 109・78互換包摂 29・統合適用 28。代用字は
1 文字とは限らず、37 件は代用字自体が外字注記になっている（`→［包摂適用 ※［＃「（冫＋
臣＋犯のつくり）／れんが」、第3水準1-87-58］］`）。

## 符号位置を持たない 1155 件をどう同定するか

面区点や U+ があれば字形は符号位置で決まる。問題はコードを持たない 1155 件——包摂適用・
デザイン差・統合適用、つまり「符号位置が同じで字形だけ違う」例示字形そのもの——で、
ここは PDF の字形が唯一の情報源になる。

**字形の輪郭ではなく、content stream の CID を読む。** 字形欄は非埋め込みの Ryumin-Light
で描かれているものが多く、描画系は代替フォントで CID を解決できずに .notdef（□に×）を
出す。輪郭を取っても豆腐にしかならない（この方式で 1045 件取ったうち 644 件が豆腐だった）。
一方 PDF には「どの CID を描くか」が書かれていて、Ryumin-Light は Adobe-Japan1 なので
Unicode の IVD（Adobe-Japan1 コレクション）で異体字セレクタ列に落ちる。

```
p10-4 「凡」→［包摂適用 凡］規準37
    content stream:  1 0 0 rg /F8 Tf [<36d9>]TJ   ← 赤・Ryumin-Light・CID 14041
    IVD:             CID+14041 → U+51E1 U+E0101
```

| 同定できた手段 | 件数 |
|---|---|
| **IVS（Adobe-Japan1・CID から直接）** | **799** |
| MJ 文字図形（輪郭照合。`gaiji_chuki_mj.tsv`） | 137 |
| IDS から字（説明の組み立てから） | 332 |
| GlyphWiki の合成グリフ名 | 572 |
| **いずれかで同定** | **1103（95%）** |
| どれも無い | 52 |

埋め込みサブセットフォントの CID はそのフォント内でしか意味を持たず ToUnicode も無いので、
そちらは輪郭を残すしかない（272 件）。

## 説明文から組み立てを導く（`ids` 列）

説明文は部品の組み立てを表す小さな言語になっている。

| 記法 | IDS | 例 |
|---|---|---|
| `＋` | ⿰（左右） | `口＋畢` → ⿰口畢 |
| `／` | ⿱（上下） | `髟／舌` → ⿱髟舌 |
| `＜` | ⿴/⿵/⿷/⿶ | `囗＜力` → ⿴囗力、`匚＜工` → ⿷匚工（囲む側で変わる） |
| `−` | 対応なし | `文−亠` → 乂（左を IDS 表で分解し、部品を 1 つ取り除く） |

`＋` は普通 ⿰ だが、垂れ（`广`・`疒`）は ⿸、繞（`辶`・`走`）は ⿺ になる。左の部品で
決まるので表にした（`ATTACH`）。`鹿` は IDS 表でも ⿸128 対 ⿰46 と割れていて、辞書の
6 件は ⿰ 側だったので入れていない。

引き算は左を IDS 表で分解して部品を取り除く。`草−十` は `草 = ⿱艹早`・`早 = ⿱日十` から
`⿱艹日`。**呼び名を持つ部品（`艹`・`亻`…）はそれ以上ばらさない**——ばらすと `艹` が `十十`
に見えてそちら側から引かれてしまう。組み上げた部分 IDS は IDS 表で字に畳む（`⿸广⿱艹日`
→ `⿸广䒤`）。

**畳んだ先が BMP 外になるのは、それで字が引けたときだけ。** `⿱刀⿰刀刀` は `⿱刀𠚪` に
畳むと 刕 が引けるので畳むが、`⿱自儿` を 𧠆 (U+27806) に替えても表現力は変わらないうえ
Ext-B の無いフォントで読めなくなるだけなので、そういう畳み方は戻す。それでも `ids` の
354 件は BMP 外の字を含む——`挿のつくり` が `𢆍` (U+2218D) であるように、部品そのものが
BMP 外の場合で、これは書き換えようがない。

部品は文字そのもののほか「にんべん」のような呼び名や「膠のつくり」のような他の字からの
参照で書かれる。前者は `tools/gaiji_ids.rb` の語彙表、後者は CHISE の IDS 表の分解で解く。

### `「A」の「B」に代えて「C」`

説明の外側にもう一段ある書き方で `desc` の 1020 件。A を組み立ててから B を C に差し替える。
`「尅」の「寸」に代えて「土」` は `尅 = ⿺克寸` から **`⿺克土`**、`「曼」の「日」に代えて
「瑁のつくり−目」` は `⿳日罒又` から `⿳冃罒又`。`、` で continue する 2 段重ねもある。

位置指定つき（`の左の「人」に代えて`）と、A が入れ子の注記になっているものは拾わない。
どの部品を差し替えるのか一意に決められないため。

**効かせるのは、そのエントリが符号位置を持たないときだけ。** この書き方には 2 通りある。

```
7． 挪 ※［＃「てへん＋那」の「二」に代えて「はみ出た横棒二本」、U+632A］   字は 挪 のまま。字形の細部
7．    ※［＃「尅」の「寸」に代えて「土」、ページ数-行数］                符号位置が無い。組み立てそのもの
```

U+ が印字されていれば字は決まっていて、`代えて` は字形の注記でしかない。ここで差し替えると
`⿰扌那 → 挪` という正しい同定を壊す（試すと一致が 68 件減った）。符号位置があるときは
土台だけを組む。

B と C が同じ部品に解決される組もある（`「者」に代えて「睹のつくり」`。異体の 者で、IDS
では書き分けられない）。そのときは木をばらさず、組み立てを残す。

**CHISE が `①`〜`⑳` で書く部品まで分解したら諦める。** 符号位置の無い部品の代用記号で、
`⿱⑥廾` は何も同定していない。以前は 5 件そのまま出ていた。

**規則の妥当性はデータ自身で検算できる。** 符号位置を持つエントリで「説明 → IDS →
IDS 表 → 符号位置」がエントリ自身の U+ と一致するかを見ると、字が引けた 6152 件中
6035 件が一致した（**98.1%**）。不一致 117 件は `にんべん＋蜈のつくり → 俣 / 俁` のような
字形の揺れで、辞書と CHISE のどちらが正しいか判断が要る性質のもの。

`ids` が 1 文字に落ちたものは `ids_char` に入れていない。引き算や `〜のつくり` の結果が
1 文字になった 283 件で照合すると一致は 79% しかない。辞書がそれらを外字として載せて
いるのは、まさに部品そのものとは少し違う字形だからで、当てにならない。

符号位置が無い組み立ては GlyphWiki の合成グリフ名で参照できる。`旬＋力`（『小公女』が
底本の字形を示すために使っている字）は <https://glyphwiki.org/wiki/u2ff0-u65ec-u529b>
に実在する。部品が増えるほど登録は少なくなる。

## PDF と食い違っていないかを見る

```
ruby tools/verify_gaiji_chuki.rb gaiji_chuki.pdf [--html tmp/gaiji_chuki.html]
```

抽出器を通さずに確かめるのが要点。抽出器のロジックで検算しても同じ思い違いをなぞるだけ
なので、逆向きに **TSV の列から注記を組み直して、それが PDF の本文に出てくるか**を見る。
`desc`・面区点・水準・U+・代用字とその種別・規準番号が一度に効き、1 文字ずれれば落ちる。

```
TSV:      desc=「尅」の「寸」に代えて「土」
組み直し:  ※［＃「尅」の「寸」に代えて「土」、ページ数-行数］
PDF p34:  7．   ※［＃「尅」の「寸」に代えて「土」、ページ数-行数］     ← 出てくれば ✓
```

`ページ数-行数` と `補助のみ`／`補助漢字と共通` は TSV に持たない飾りなので、両側から
落として比べる。前者は付き方が辞書側で揺れてもいる（符号位置も代用字も無い 232 件は
162 対 70）。結果は 3 段階。

| | 件数 | 意味 |
|---|---|---|
| ✓ | 10189 | そのまま出てくる |
| ? | 21 | 説明は出てくるが注記の形が違う。閉じ 」 落ち 12・`（` で始まる説明の括り 3・PDF が 2 行に折り返している 5・番号が括弧の内側 1 |
| ✗ | 0 | 説明ごと見つからない＝本当の食い違い |

**`cross`（★）と `strokes` は PDF の印字を直に読んで照合する。** エントリの頭は
`★ 16． 坪` の形なので、ページごとに `(★, 画数)` の並びを取り出して TSV と突き合わせる。
注記の有無では数えない——字形が複数行にわたると ★ と注記が別の行に来る。179 ページすべて
一致する。

**`radical` は並びで見る。** 節見出しから状態として引き継ぐので、1 つ取りこぼすと以降が
まとめてずれる。TSV に出る部首の順序が PDF の見出しの順序の部分列になっていればよい
（見出しがあってもエントリが 0 件の節はある。`釆` は `0． 釆 采 入力可能` の 1 行だけ）。

**`id` の付き合わせも見る。** `id` は `p<ページ>-<ページ内連番>` なので、本体にエントリが
1 つ増えると以降の連番がずれる。輪郭も MJ も id で紐づいているから、本体だけ作り直すと
黙って別の字を指す（実際にこれで MJ の 137 件中 25 件がずれた）。`sub` と `desc` で
裏を取る。

**裏の取れていないもの。** `ivs` と `cid` は PDF の content stream から取った値で、機械的に
突き合わせる独立な情報源が無い（目視の手だては次節）。復元の照合は「そのページのどこかに
出てくるか」なので、同一ページ内で注記が完全に同じ 27 件は入れ替わっても気づけない。復元の
規則は HTML 生成器と共有しているので、抽出器からは独立だが両者が同じ勘違いをしていれば通る。

## `ivs` / `cid` を目で確かめる

```
ruby tools/gaiji_chuki_ivs_sheet.rb   # 既定は tmp/gaiji_chuki_ivs.html
```

1071 件を並べた検分用の一覧。**左に代用字（包摂される側の標準の字）、右にこの辞書が示して
いる字形**を置く。同じ字の書き分けに見えていれば結び付けは正しく、まったく別の字に見えたら
CID を隣のエントリのものと取り違えている。

字形の出し方は 2 通り。IVS がある 799 件はブラウザに描かせる。IVS が引けなかった 272 件は
PDF から取った輪郭をそのまま置く——こちらは辞書が実際に描いている形なのでフォントに依らない。

**複数のパーツで組んである字は、パーツを全部拾って合成して見せる。** `三／二` は 三 と 二 を
上下に、`⿰冫虫` は 冫 と 虫 を左右に、別々に置いてある。以前は先頭だけ採っていたので
`⿰冫虫` に 冫 の CID が付いていた。いまは `ivs` が ` / ` 区切りで全パーツを持ち
（`4E09 E0100 / 4E8C E0100`）、一覧は `ids` の演算子を見て縦積みか横並びで組む。34 件。

ただし **CID が字の同定になるのは非埋め込みの Ryumin（Adobe-Japan1）だけ**。Ryumin と
埋め込みフォントのパーツが重なっている字が 11 件あり、埋め込み側の CID を IVD に通すと
無関係な字が出る（`「にんべん＋充」の「儿」に代えて「冉」` に 侫 と 控 が付いていた）。
混ざっていたら `ivs` は付けず、輪郭に回す。

それらは**輪郭も二重写しになる**。poppler が Ryumin の CID を代替フォントで解決できず
別の字を描くためで、PDF をそのまま画像にしても同じに見える。

**辞書は「部品を描いては白い矩形で消す」手順で字形を組んでいる。** content stream を見ると
はっきりする。

```
BT /F24 8.291 Tf -2.8 -626.2 Td[<11d4>]TJ ET     侫（CID 4564）を描く
1 G 1 g  q -.14 -630.19 14.27 14.27 re f Q       その上を白で塗りつぶす
0.5 G 0.5 g  BT … Td[<0279>]TJ ET                 次のパーツを描く
```

マスクを落とすと部品が全部重なってつぶれる。`page_glyphs` は `<use>` に加えて**白い塗り
つぶしも描いた順のまま拾う**。`gaiji_chuki_glyphs.tsv` に `dy` と `ivs` を足し、マスクも
1 行として並べてある（15 行）。表示側は行の順に `dx`・`dy` だけずらして重ね、
マスクは地の色で塗る（`<path>` は transform、`<text>` は座標に足す。
描画と viewBox の**両方**に効かせること——外接矩形で忘れると上が切れる）。`dy` は縦に積む字（`三／二`）に効く——パーツごとにベースラインが違うので、
捨てると上下が重なる。パーツと run の照合も x だけでは足りず（縦積みは x が同じ）、
y も見る。

もう一段ある。poppler は非埋め込みの Ryumin の CID を代替フォントで解決できず別の字を
描くので、そのパーツは輪郭を捨てて `ivs` と `box` を持たせた（81 パーツ）。表示側は
`<text>` を `box` に流し込む。**字の正しさは IVS から、大きさは content stream の変形から**
取る。辞書はパーツを横 0.7 倍などに潰して組んでおり（`.7 0 0 1 0 0 cm`）、等倍で置くと隣の
パーツと重なる。`tools/pdf_text_runs.rb` はもともと平行移動しか見ていなかったので、CTM を
行列で追うようにして各 run の全角 1 文字ぶんの寸法（`sx`・`sy`）を出している。

パーツと run の対応は位置で取るが、**同じ run を二度使わない**こと。`竹かんむり／擧` は
2 つのパーツが 0.17 しか離れておらず、近さだけで選ぶと両方が同じ run に当たって、下半分が
上半分と同じ字になる。

```
「にんべん＋充」の「儿」に代えて「冉」
  1. <text>侫</text>        Ryumin の CID 4564。読み手の Adobe-Japan1 フォントが描く
  2. <path class="mask">    白い矩形。侫 の右側を消して 亻 だけ残す
  3. <path>亠厶冉の輪郭</path>  埋め込みフォントのパーツ
```

複数パーツの字はすべてこの経路に送る。CID 1 つでは字を指せないし、パーツの CID を並べても
字にならない（`土へん＋奇` は 坪 を描いて 平 を消したもので、坪 でも 奇 でもない）。

この切り分けの鍵は**字形と注記の間に入る空白（CID 633）**だった。これをパーツと数えると
ほぼ全件が「複数パーツ」になり、正しく取れている 189 件まで巻き添えで落ちる。除いたところで
判定が一致した。

赤枠は残り 1 件（p127-32 `くさかんむり／椛のつくり`）。単独のはずなのに基底字が `花` で、
`⿱艹花` の部品を指している。`verify_gaiji_chuki.rb` が同じ判定で報告する。

黄枠の 87 件は IVS の基底字が代用字と違うもの。異体字自身が符号位置を持つ場合（`倂` と
`併`）で、それ自体は正常。

**この一覧で分かるのは結び付けだけ。** CID の値そのものが正しいかは分からないし、同じ
代用字を持つエントリ同士で 1 つずれていても見つからない。また **IVS はブラウザのフォント
任せ**で、Adobe-Japan1 の異体字セレクタに対応していないと左右が同じ形に見え、その場合は
判断できない（macOS の Hiragino は対応する）。

## 同定できていないものを見る

`ruby tools/gaiji_chuki_gaps.rb` が同定の強さで段階分けして数える。下 3 段——親字しか
分からない 0・組み立て式だけ 50・説明文しかない 6——の 56 件が符号位置にも代用字にも
字形にも届いていないもの。

残る「説明文しかない」6 件はそれぞれ理由が違う。

| id | 詰まったところ |
|---|---|
| p49-2 / p132-27 | `「座」の左の「人」に代えて「ヌ」`。位置指定つきで、どの `人` か決まらない |
| p70-36 | `月＋（「亶」の…）`。説明の中に注記が入れ子 |
| p133-25 | 置換先 `面から一、二画目をとったもの` が自然言語 |
| p120-42 | 置換先 `黨−尚−れんが` の `黨` を IDS 表が `⿱𫩠黑` と書いていて、`尚` が引けない |
| p128-28 | `くさかんむり／（夷−十）`。`夷 = ⿻大弓` に `十` が無い |

辞書 PDF 側に**閉じ「」」が落ちた注記が 12 件ある**（`※［＃「りっしんべん＋乞、第 4水準
2-12-32］`）。`split_spec` は閉じが無くても、後ろに続く符号位置と区切りの 、 を削って説明を拾う。

## HTML 版

```
ruby tools/build_gaiji_chuki_html.rb [出力先.html]   # 既定は tmp/gaiji_chuki.html
```

この TSV から 1 枚の HTML（7.4 MB）を組む。出来上がりは外部リソースを一切参照しない
自己完結（初回のビルドだけ GlyphWiki への通信が要る。後述）。

見出し・絞り込み・部首索引は左の脇柱に固定して、本文は最初から出す。索引は 202 部首ある
ので脇柱自体を縦スクロールさせ、820px 以下では畳んで頭に載せる。

PDF 版に対する利点は 4 つ。**符号位置を持たない字が見える**——`gaiji_chuki_glyphs.tsv` の
輪郭 224 字をインライン SVG で埋めるので、フォントに無い字も字形が出る。**絞り込める**
——説明・面区点・U+・代用字・種別（`包摂適用`）・IDS・id を対象に、打った端から。条件は
`?q=` に残るので URL で渡せる。**項目に飛べる**——`#p34-17` でアンカーが張ってある。
**注記がコピーできる**——`※［＃「尅」の「寸」に代えて「土」、ページ数-行数］` の形に組み
直してあり、そのまま本文に貼れる。

字形は確かなものから順に落として出す。輪郭 → 面区点の字 → U+ の字 → IVS → `ids_char`。
何を出したかは各項目の隅に「輪郭」「面区点」のように書いてある。IVS は対応フォントでないと
基底字に見える。

**BMP 外の字は GlyphWiki のグリフを焼き込む。** `U+207C2`（曾＋りっとう）のような Ext-B
以降はフォントに無いことが多く、そのままだと豆腐になる。該当する 548 字を
<https://glyphwiki.org/glyph/u207c2.svg> の形で取り、`<symbol>` にして先頭にまとめ、
本文からは `<use>` で参照する（延べ 1600 箇所ある字形を 1 つずつ持たずに済む）。グリフは
登録時に著作権が GlyphWiki に譲渡され事実上パブリックドメインなので焼き込んでよい。

SVG フォント（`<font>` 要素）は仕様として廃止されていてどのブラウザも読まないため、
`<symbol>` ＋ `<use>` で同じことをしている。`fill:currentColor` にしてあるので、本文の
色や `font-size` にそのまま追随する。

初回だけ通信が要る（548 字・2 分ほど）。取ったものは `GLYPHWIKI_CACHE`（既定
`tmp/glyphwiki`）に置いて使い回す。引けなければ警告を出してフォント任せに戻るだけで、
ビルドは通る。異体字セレクタ（`U+E0100`〜）は不可視の制御文字なので焼き込まない
——GlyphWiki には `ue0101` に「VS18」という枠付きの代替グリフがあり、出すと本文に見える。

輪郭の色は辞書の凡例（緑＝例示字形変更、赤＝包摂される字、灰＝参考掲載）に対応させたが、
原典の原色は薄い背景で読めないので濃くしてある。

## `gaiji_chuki_mj.tsv` — 輪郭照合で特定した 137 件

`tools/match_glyphs_ipamj.rb` で作る**任意の**成果物。IPAmj明朝がライセンス同意の先に
あり、MJ 文字情報一覧表も別途入手が要るので、抽出器本体とは分けてある。対象は `glyph=1`
の 272 件で、代用字の異体字を IPAmj明朝から描いて重なりの良いものを選ぶ。

較正では、正解と分かっているペアの IoU が中央値 0.61、無関係なペアが 0.22 で分離する。
`iou>=0.40` かつ 2 位と 0.05 以上の差があるものだけを載せた（137 件・IoU 中央値 0.95）。
`runner_up` と `candidates` を残してあるので、確度は利用側でも判断できる。

IoU は塗り方の実装に敏感で、走査線の丸めが違えば 0.02 ほど動く。**どの MJ 図形を選ぶかは
変わらない**（先に Python で書いた版と共通 135 件すべてで一致した）が、閾値ぎりぎりの
ものは出たり出なかったりする。件数を当てにせず `iou` と `runner_up` を見ること。

## 取り込むときに引っかかったこと

- **表示字形は文字として取らない。** 外字は ToUnicode を持たない埋め込みサブセット
  フォント（GT2000・花園明朝など）で描かれ、pdftotext は BMP 外の字を別の字に取り違える
  （U+ を持つ 4021 件中 186 件が食い違い、うち 141 件が BMP 外）。正は注記本文であり、
  そちらはかなと常用漢字と ASCII だけなので確実に取れる。
- **制御文字。** 同じ理由で、字形は U+001E などの制御文字として出てくる。XML として
  不正なので落とす（位置しか使わない）。
- **描画系の豆腐を字形と取り違えない。** 非埋め込みフォントの字は .notdef になるので、
  輪郭を取ると □に× が入る。CID を読む方式に変えた理由がこれ。
- **`ページ数-行数` はプレースホルダ**（「ここに底本のページ-行を書く」という指示）
  なので取り除いてある。

## 使い道

変換経路には入れない。参照実装 aozora2html はこの辞書を持たないので、いま `※` で
出ている字を解決し始めると出力が変わり、オラクル（byte 一致）が悪化する。想定して
いるのは次の 2 つ。

- **診断** — 辞書に無い綴りの検出（入力ミス）、代用字の提案。`analysis` の診断は
  docs/plan-lsp.md
- **生成側の支援** — 字から慣用の注記を引く逆引き（スキャン画像からの生成など）

コーパス全 17509 作品で、面区点を持たない注記は 7029 箇所 / 2735 種あり、`desc` で
引けるのは 3395 箇所 / 820 種（うち 770 種は字が一意に決まる）。引けないものは説明の
書き方の揺れが多く、正規化でさらに拾える余地がある。
